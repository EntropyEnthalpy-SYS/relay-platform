# 跨节点总流量额度（0.4.0 起；0.14.0 增加原状态恢复）

此功能约束已接纳的应用负载，上下行合计。一个用户在两个节点各传输一份数据，会共同消耗同一用户额度；适用的租户和节点额度同时扣除。一个字节在每个约束层级分别记一次，不应将不同层级的 `consumed_bytes` 相加当作业务总用量。

## 配置步骤

1. 在所有受影响节点停用该用户、租户或节点对应的规则，等待期望修订与实际修订一致且无应用错误。新建对象尚无规则时可直接配置。
2. 创建共享额度，选择对象、总字节数和单次预留大小。每个对象只保留一个额度，便于维护不可重置的累计账。
3. 重新启用规则。控制器自动生成 `budget_ids`，Agent 按这些 ID 执行约束。客户端省略或篡改 ID，或回滚旧配置，都不能取消当前适用的预算。
4. 补流量使用修改总额度；期望修订过期返回 409。额度不能降到已消费与未归还预留之和以下。

创建预算的屏障要求离线节点也确认暂停；这种情况下应等待节点恢复。当前没有强制撤销离线运行配置的接口，也不会把未确认节点视为已经停用。

## 数字的含义

| 字段 | 含义 |
| --- | --- |
| `limit_bytes` | 本预算可承诺给所有节点的累计字节上限 |
| `consumed_bytes` | 控制器已收到并去重的累计接纳量 |
| `committed_bytes` | 已消费量加所有尚未归还的预留，包含节点尚未上报的消费 |
| `committed_bytes - consumed_bytes` | 仍占用总额度的预留；不是一定未使用的字节 |
| `limit_bytes - committed_bytes` | 控制器可以分配的新额度 |
| `quantum_bytes` | 单次预留目标大小，允许 1 字节到 64 MiB；小批次减少占额，大批次减少控制交互 |

预留不是保证带宽的租约。当前没有按节点公平轮转或限速分配；较大的预留可能让其他节点暂时无额度可领。多个层级同时约束时，还可能在某一层耗尽而其他层存在预留；未消费部分会按正常封存规则归还。

## 运行与故障合同

- 控制器原子执行预留发放、累计消费与未用部分归还。相同请求返回相同预留；报告重复、乱序或归还重试不会再次扣量/退款。封存后的消费边界不能增加。
- Agent 先在一个事务中检查规则和全部适用预算，再更新所有消费记录。磁盘事务失败不会转发对应负载。
- 缺额时按规则 `connect_timeout_ms` 等待补额，超过后终止对应 TCP 方向或丢弃该 UDP 包。TCP 缓冲区内已经读取但尚未获准的部分会保留到补额或超时；连接和队列上限继续约束内存。
- UDP 不拆包扣量。单包大于 `quantum_bytes` 时，Agent 可要求足以容纳完整包的最小预留；最多 65536 字节，且不能突破预算剩余总额。上下行分别获准，上传获准不保证回包还有余额。
- 控制器暂时不可达，持续运行的进程可消费现有预留；严格节点还受剩余租约有效期约束，不能无限延长额度。正常补额触发有 2 ms 合并等待；请求未获新额度时等待 100 ms，控制请求失败时等待 500 ms，常规心跳可更早触发。有预算节点的心跳间隔不超过 500 ms。慢控制链路可能降低吞吐，需实测后选择批次。
- 所有业务会话空闲时封存本次运行的预留，接着归还未消费部分。UDP 缓存会话在空闲回收前仍算活动会话。一个节点还有其他活动会话时，当前实现不会逐用户主动回收空闲额度；停用相关规则会触发对应预算封存。
- 有序停止先等待转发退出与本地计量提交，再结算最后用量和待确认请求，最长等待 2 秒。控制器已发放但回复丢失的预留会被找回并封存归还；尚未发放的请求会记录取消状态，防止较晚到达的原请求再次占额。已封存报告可在后续启动重试；未完成结算的旧运行未知预留仍保守占额。
- 创建新预算运行时，旧运行仍开放的预留变为 abandoned，不消费、不自动归还。0.14.0 允许严格节点在原状态完整、所有权连续并完成全部预留验证后延续原运行；逐项核对和补报在监听启用前完成。验证失败时不开监听，也不执行可能退款的普通停止清理，见 [BUDGET_RECOVERY.md](BUDGET_RECOVERY.md)。
- 普通规则周期切换不会清零预算。预算的周期自动重置、到期、删除、未知消费的权威回收和端口组/共享资源预算均未完成。0.13.0 的严格节点使用执行租约绑定预算运行编号；租约到期不自动退款，见 [NODE_LEASES.md](NODE_LEASES.md)。

## 备份与恢复限制

跨节点预留需要 `relay agent` 与控制器同步；`standalone` 无法分配全局预留，使用含 `budget_ids` 的受管配置会拒绝对应流量。

每份控制器导出备份都带 `budget_allocation_paused:true`；源数据库保持原状态。只有旧备份不能证明后来发放了多少预留，因此不能直接恢复分配。已知报告可以对账；快照遗忘的预留报告返回 409，Agent 停止转发以保护账本边界。

0.4.0 增加控制器恢复日志。`relay restore` 使用启用日志后的备份、完整日志及最新进度清单，恢复节点凭据、配置、所有已提交的预留与消费记录，再恢复源数据库原有的分配状态。如果源状态本来就在隔离中，恢复仍保留隔离。没有仅清除标记的 HTTP API；日志缺失、校验失败或历史不连续时拒绝恢复。详见 [RECOVERY.md](RECOVERY.md)。

受管旧节点备份仍先执行规则账本分页对账；导出时移除续接标记，它不会重新开放旧运行的预留。原数据库正常重启的恢复条件与备份恢复分别处理，不能通过复制恢复标记使旧快照变成最新状态。直接篡改数据库、手动清除隔离标志、复制正在运行的内存或使用未知来源旧文件系统快照不属于受支持的恢复流程。完整全节点灾难恢复仍在待实现范围。

## 验证

`tests/budgets.rs` 验证多节点并发发放、重复请求、层级原子扣量、事务回滚、有序归还、旧副本保护、权限、恢复隔离，以及结算先到/原请求先到两种顺序。`tests/control_agent.rs` 使用真实 HTTP、TCP、UDP 和两个实际 Agent，覆盖连续补额、总额耗尽、加额、控制器中断、完整 UDP，以及旧控制备份重放后在同一 TCP 连接继续补额。

`scripts/bench_budget.py` 通过真实 Release 子进程对比开启预算前后的吞吐，并核对全部载荷、节点账本、控制器规则账本和用户额度，以及停止后未用预留归还。它与无预算 `bench_loopback.py` 是不同基准，不能混用数据。浏览器交互、真实 Linux/WAN 与长时间压力仍未验收。
