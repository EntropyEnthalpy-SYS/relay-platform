# 原状态额度恢复（0.14.0）

严格节点的进程意外退出后，如果原 Agent 数据库完整保留，且控制器确认期间没有其他运行接替该身份，Agent 可以在线核对原预留、补报持久化消费并继续使用确认后的余额。恢复全部完成前不开启业务监听。它解决的是原状态重启时余额被永久搁置的问题；未知消费仍保守占额。

## 适用条件

| 条件 | 本版本处理 |
| --- | --- |
| 0.14.0 严格节点的原状态完整保留，控制器历史连续 | 等待原租约失效，领取新代数和新令牌，验证后延续原预算 run_id |
| 通过 relay backup 导出的节点副本 | 导出时移除续接资格，执行原有对账并新建预算运行；原开放预留不复用、不自动退款 |
| 原实例退出后已有其他运行接替 | 恢复申请返回 412，Agent 换新 run_id/token 申请；旧未知预留保守占额 |
| 离线策略，或升级前状态没有续接标记 | 新建预算运行，不恢复旧开放预留 |
| 控制器历史缺失、分配隔离，或本地消费低于已确认边界 | 拒绝恢复，业务监听关闭，不将未验证余额作为退款依据 |
| 原状态没有未结预留或待确认请求 | 直接走新预算运行，不需要恢复 |

原数据库中的续接标记只记录预算 run_id 和最后代数，不是抵抗原始文件复制、VM 快照回退或人为篡改的真实性证明。这些操作可能同时复制标记与过时的消费状态，不属于已经验收的恢复流程。进程在领取成功与本地持久化之间再次退出，也可能失去连续性证明；当前选择保守占额，不猜测恢复资格。

本功能要求单一权威控制器。控制器从完整原状态重启，或用最新完整日志重建后，可以继续验证；仅有旧控制器备份仍保持分配隔离。双端状态同时丢失、任意旧快照恢复、强制退款和多控制器共识没有完成。

## 启动与恢复顺序

1. 读取本地续接标记。只在存在原运行未结记录时提出恢复申请。
2. 使用新的随机运行令牌申请租约，携带原 run_id 和 resume_generation。控制器要求其最后持有者仍为同一运行、代数仍相符。原租约仍有效或冷启动保留期尚未结束时返回 423；Agent 等待，不先修改预算状态。
3. 领取成功会增加所有权代数。本地原运行和新代数在事务中更新，保留已有消费、预留与待确认请求。进程身份由新代数和新随机令牌约束，run_id 可跨进程延续。
4. 先完成规则账本对账，再发送恢复清单。清单包括原运行全部未结预留的完整身份、累计消费和封存状态，以及未收到最终回复的预留申请。
5. 控制器校验节点凭据、当前租约、恢复来源、账本归属和每条预留。消费不得低于服务端确认值，也不得超过分配量；已经关闭的预留只能按封存状态处理。任一校验失败，整页不提交。
6. 有效记录在同一事务中补报消费，并写入恢复审计。已发放但回复丢失的请求找回原预留；从未发放的申请记录取消，防止迟到的旧请求重新占额。该接口不额外发放新额度。
7. Agent 验证回复覆盖所有请求、没有重复身份且消费边界未改变，再持久化回复。所有页成功之后才应用配置并开启监听；普通同步再按原规则补报账本、申请新额度和有序结算。

一次恢复最多读取 65,536 份未结预留与 65,536 个待确认请求，每次请求分别最多 512 条，仍受 HTTP 2 MiB 限制。多页不是一个跨网络事务：先前成功页面可被重复确认，后续失败时仍不开启业务。等待恢复期间继续续租，并受独立本地租约期限约束。

网络超时不能证明控制器没有提交。恢复使用原请求身份重试，重复补报不重复扣量，重复找回不再发放额度。这个故障分类也见 [etcd 官方 API 的完成语义说明](https://etcd.io/docs/v3.6/learning/api_guarantees/#operation-completed)；本平台没有使用 etcd，也不具备其多成员共识保证。

## 失败与余额处理

恢复预检尚未完成时，Agent 不走可能封存并归还未验证预留的普通停止结算，也不提前释放租约。原状态保留，监听保持关闭。修复控制器可用性或权限后可用同一原状态重启；下一次仍须证明所有权连续并重新验证。

成功恢复后，已有的业务空闲策略仍然生效：没有活动会话时可能立即封存、归还已经验证的未使用余额；后续业务正常申请新预留。因此“延续原运行”不保证每份原 grant 都会再次用于业务。

总额度仍按已确认消费加未归还预留限制分配。租约过期、节点离线或明细中的 outstanding_bytes 都不是“这些字节没有被消费”的证明。对端已确认但节点尚未收到的回复，可以按身份找回；两端都缺失的消费不能凭本功能重建。

## 操作与观察

意外退出后先确认使用的是原私有状态目录，然后用原 node_id 和 controller 地址重新启动 Agent。不要用备份替换原数据库，也不要手工修改 metadata。启动期间保留日志，等待租约、对账及恢复全部完成后再验收真实 TCP/UDP。控制器冷启动时，即使原 Agent 已退出，也需经过一个完整 TTL 的接替等待。

“节点管理 → 运行诊断”显示本次监听启用前的恢复时间、run_id、已验证预留数、找回请求数、取消请求数与当时仍有余额的开放预留数。它是一次历史结果，不是实时余额；正常停止的最后一次心跳仍保留该结果。

“流量额度 → 预留明细”按租户权限只读展示开放预留，每页最多 100 条。尚占用量等于分配量减控制器已确认消费，包含节点未上报的部分；当前节点租约属于节点现在的持有者，不能推断每份历史预留都由当前运行消费。多页读取期间记录可能变化，不提供固定时点的结算快照。

## 升级与验收

先升级控制器，再升级 Agent。数据库 schema v4 没有新增表，但租约元数据增加恢复来源，Agent 同步增加可选诊断；旧版严格解析器不能直接读取这些新增字段。已使用恢复的状态不能仅凭 schema 数字不变而降级到旧控制器。0.13.0 的未知开放预留不会因升级自动取得恢复资格。

自动化覆盖连续所有权、失去连续性、回复丢失、层级待确认请求、备份移除资格、账本归属、消费边界、事务失败、权限和 100/100/1 分页。真实 HTTP/Agent 测试覆盖恢复回复提交后丢失、TCP/UDP 在恢复期间关闭、失败时不退款，以及旧备份接替后原状态不得复用旧预留。

独立 Release 子进程演练可重跑：

```sh
python3 scripts/check_budget_recovery.py \
  --binary target/release/relay --output artifacts/budget-recovery-smoke.json
```

它停止控制器，在剩余有效租约内制造尚未上报的 TCP/UDP 用量，再 SIGKILL Agent；重启原控制器和原 Agent 状态，验证等待、补报、额度用尽后的拒绝以及最终三份账本。它不安装系统服务，临时进程均清理。当前版本结果见 [VALIDATION.md](VALIDATION.md) 和 [原始演练记录](budget-recovery-smoke.json)。Linux 实机、真实断电、文件系统损坏、浏览器点击与长期网络分区仍待各自验收。

## 额度灾难恢复（0.136.0，可选功能，默认关闭）

原状态丢失（换盘、重装、身份替换）或控制器从旧备份恢复后，上面的在线核对无法进行。系统管理员在「可选功能」开启 `budget-recovery` 后，「恢复保护」页提供两个审计操作。两者都按最坏情况处理：未知用量计为已消耗，不退回；需要更多额度时由管理员调高上限。

- **核销运行**：列出每台节点每次运行的未结束预留及其状态。持有执行租约且仍有效的运行为“使用中”，不能核销；已被其他运行接替但交接窗口未结束的返回 423；窗口结束后为“已停止”，可直接核销；没有执行租约的节点（或租约到期但仍是最后持有者的运行）必须由管理员确认旧进程已停止。核销把这些预留的剩余字节加入已消耗并关闭预留，已承诺字节不变。旧进程之后的报告不会超过关闭边界；它自己的 Agent 会拒绝继续使用已关闭的预留。核销后节点删除不再被这些预留阻止。
- **结束恢复锁定**：仅在旧备份留下的分配锁定存在时可用。管理员按当前修订确认全部额度，控制器把每个额度的剩余空间（上限 − 已承诺）计为已承诺和已消耗，删除锁定及备份标记（重启和迁移不会重新锁定）。备份遗忘的预留仍会被拒绝（409），对应节点按节点身份流程替换后再核销旧运行。
- 每个操作带客户端生成的操作编号；重放同一编号返回原回执，不重复计数。回执显示在「恢复记录」并写入审计 `budget.recovery.write_off|quarantine_exit`。
- 接口（仅系统管理员会话，API 令牌被拒绝）：`GET /recovery/budgets`、`POST /recovery/budgets/runs/{node}/write-off` `{operation_id, run_id, reason, stopped_confirmed}`、`POST /recovery/budgets/quarantine/exit` `{operation_id, reason, budgets:[{id, expected_revision}]}`。功能关闭时写操作返回 409。
- 不包含：凭旧 Agent 数据库证据退还部分字节、自动替换节点。
