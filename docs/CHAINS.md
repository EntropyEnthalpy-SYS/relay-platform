# 端点组与转发链：按层复用的多跳转发

端点组（英文界面 Endpoint group）是转发链中的**一层候选服务器**；转发链（Chain）把端点组按顺序排成 1–6 层。用一条转发链新建转发时，路径为：客户端 → 入口服务器 → 第 1 层候选 → 第 2 层候选 → … → 最后一层候选 → 最终目标。它对应 Zero Forwarder 的“端点组”和“已保存的转发链”。

同一个端点组里的服务器**互为备选**，不是依次经过的多跳：上一跳按这一层的均衡方式在组内选择一台。需要经过几跳，就建几层，每层一个组。

转发链只是“生成规则的模板”。用它新建的转发由每台服务器上的**普通规则**组成（目标带 `via` 指向下一层服务器上的规则，见[拓扑](TOPOLOGY.md)），之后的修改、暂停、删除、健康检查和计量都与手工搭建的多跳转发相同。

## 数据与安全边界

- Agent 协议、发给 Agent 的规则格式都没有变化，旧版 Agent 照常运行。schema、恢复日志格式、备份和连续恢复也不变。控制器在 `metadata` 中另存三类记录：
  - `endpoint_group:<id>`：`{id, tenant_id, name, description, members:[node_id], created_at_ms, updated_at_ms}`，`members` 按操作者给出的顺序保存；
  - `forwarding_chain:<id>`：`{id, tenant_id, name, enabled, layers:[{group_id, balance}], created_at_ms, updated_at_ms}`；
  - `chain_use:<入口规则 id>`：`{chain_id, entry_node_id, layers:[[{node_id, rule_id}]]}`，记录一次“用转发链新建转发”在每层每台服务器上建出的规则。
- 端点组属于其成员服务器所在的租户，所有成员必须属于同一租户；转发链属于其端点组的租户，所有组必须属于同一租户；入口服务器也必须属于该租户。其他租户看不到这些记录，访问返回 404。
- 读取需要登录会话或带 `read` 的 API 令牌。新建、修改、删除、规划（plan）和应用（apply）需要可写角色，API 令牌还需 `nodes:write`；只读用户（viewer）返回 403。保存端点组时检查对每台成员服务器的写权限；应用时每台服务器的写权限、修订号和配置校验由配置发布路径检查。
- 应用在**一个事务**里分配端点、以一个配置批次（最多 64 台服务器）发布入口和每层的全部规则，并写入 `chain_use` 记录；任何一台失败则全部不变。
- 审计动作为 `endpoint_group.create`、`endpoint_group.update`（详情含修改前的成员）、`endpoint_group.delete`、`forwarding_chain.create`、`forwarding_chain.update`、`forwarding_chain.delete`（详情含遗忘的使用记录数）、`forwarding_chain.apply`（详情含入口与各层的规则）。发布本身仍记录 `config.publish`，涉及多台时另有一条 `config.batch_publish`。

## 限制与校验

| 项目 | 限制 | 违反时 |
| --- | --- | --- |
| 端点组成员 | 1–32 台、不重复、同一租户，名称 1–120 字节，说明最多 2000 字节 | 400 |
| 转发链层数 | 1–6 层，名称 1–120 字节 | 400 |
| 同一端点组 | 在一条转发链中只能作为一层 | 400 |
| 同一台服务器 | 不能出现在同一条转发链的两层中（经由两个不同的组也不行） | 新建 / 修改转发链 400；修改端点组导致某条使用它的转发链出现这种情况 409 |
| 入口服务器 | 不能是转发链中任一层的成员，必须属于转发链的租户 | 400，提示它在第几层 |
| 一次转发涉及的服务器 | 入口加全部层的成员最多 64 台（配置批次上限） | 400 |
| 停用的转发链 | 不能用来新建转发；重新启用后可以 | 409 |
| 转发链的某个组已删除，或组中某台服务器已删除 | 不能用来新建转发，需先编辑组或转发链 | 409 |
| 正被转发链使用的端点组 | 不能删除，需先从转发链中移除 | 409 |

## 用转发链新建转发

请求 `{entry_node_id, name, protocol, target, entry_port|null, owner_id?, expected_revisions?}`。`protocol` 为 `tcp`、`udp` 或 `both`；`target` 是最终目标（`主机:端口`，按普通规则目标校验）；`name` 为 1–100 字节。

规则图：

- 最后一层的每台服务器各得一条规则，目标为 `target`（权重 1），均衡方式为加权轮询。
- 第 i 层（i 不是最后一层）的每台服务器各得一条规则，目标是第 i+1 层**全部**服务器上的新规则：每个目标的地址为那台服务器分配到的公开地址（`advertise`），`via` 为 `{node_id, rule_id}`，权重 1；均衡方式取**第 i+1 层**的 `balance`。
- 入口服务器得到入口规则，目标是第 1 层全部服务器上的新规则，均衡方式取第 1 层的 `balance`。
- 因此第 i 层到第 i+1 层共有“第 i 层台数 × 第 i+1 层台数”条边。例如第 1 层 2 台、第 2 层 3 台时，入口有 2 个目标，第 1 层每条规则各有 3 个目标，第 2 层每条规则指向最终目标。
- 规则名为“`name` · 1”（入口）、“`name` · 2”（第 1 层）……依此类推；所有规则都是新规则（新编号、新计量周期），启用，没有配额、到期时间和限速；所有者为 `owner_id`，省略时为操作者。各服务器原有规则保持不变。
- 每层的 `balance` 可取 Relay 已有的均衡方式：`weighted_round_robin`（缺省，与引导式新建转发相同）、`source_hash`、`least_connections`、`lowest_latency`、`random`。`lowest_latency` 需要健康探测：控制器为按最低延迟选择的那条规则自动加上 TCP 连接探测（`{"tcp":{"kind":"connect"}}`）；因此只要有一层使用最低延迟，`protocol` 必须是 `tcp`，否则返回 400。
- 只生成普通 TCP / UDP 转发，与引导式新建转发的“原生 TCP / UDP”相同：节点之间不加 WS / WSS 隧道、TLS、PROXY 或多路径，也不创建受管协议网关。需要这些功能时，用引导式新建转发或在图示编辑器中修改已建成的规则。

端点（每台服务器的监听地址和公开地址）由与 `POST /configurations/allocate-endpoints` 相同的分配逻辑按路径顺序（入口，然后各层按组内顺序）给出：端口取服务器资料“转发设置”的端口范围中、已保存配置未占用的端口，地址取转发主机（有公网端口映射时换算）。`entry_port` 指定入口端口时，入口按该服务器转发设置的监听 IP 和转发主机手工设置端点；入口没有转发设置时返回 400。分配失败时：服务器没有转发地址返回 400；端口已被占用或端口范围已满返回 409。两种情况的错误体都带 `lines:[{node_id, error}]`，指出是哪台服务器。

### 规划与应用

- `POST /chains/{id}/plan` 返回 `{entry_rule_id, hops:[{layer, node_id, node_name, rule_id, listen, advertise}], batch:{updates:[{node_id, expected_revision, rules, rate_bytes_per_sec}]}, preview}`。`layer` 为 0 表示入口，1 起为各层；`batch` 是应用时将发布的配置批次，`preview` 是对它执行配置预览（与 `/configurations/preview` 相同的校验）的结果。规划**不写任何数据，也不预占端口**。
- `POST /chains/{id}/apply` 用同样的请求重新分配并发布，返回 `{entry_rule_id, hops, published}`。规则编号由应用重新生成，与规划中的不同。为保证“发布的就是预览的”，可把规划中每台服务器的 `expected_revision` 作为 `expected_revisions:{node_id: revision}` 一并提交（面板总是这样做）：涉及的服务器集合不同或任何一台的修订已变化时返回 409，并在 `lines` 中列出变化的服务器，不修改任何服务器。不带 `expected_revisions` 时按当前修订发布，发布路径仍在同一事务内检查修订。

## 使用记录与“组成员已变化”

每次应用写入 `chain_use:<入口规则 id>`。`GET /chains` 为每条转发链列出 `uses`：入口服务器与入口规则名称、每层每台服务器上的规则（规则或服务器已删除时 `missing:true`），以及 `out_of_date` 和 `changes:[{layer, added, removed}]`。

`out_of_date` 比较转发链**当前**各层端点组的成员与建成时各层的服务器：某层增加或移除了服务器即为已过期，只调整组内顺序不算。修改转发链的层（换组、增减层）同样会使已有转发显示为已过期。

**默认不改动已建成的转发。** 修改端点组或转发链只会让已建成的转发显示为已过期，不改变任何服务器的配置，也不影响现有流量。要让转发使用新的成员，需在预览后确认“更新”，或为这条转发显式开启自动更新（见下节）。

## 更新已建成的转发

更新把一条已建成的转发改为使用各层端点组的**当前**成员，而不是重建：留下的服务器上的规则保持原编号、计量、限速和所有人工修改，只改变“下一跳”发生变化的目标；新加入的服务器复制同层一条留下规则的设置；移除的服务器上的规则在改向后停用并删除。各层服务器数可以变化，层数变化不支持（预览提示新建转发）。

### 为什么会中断转发

已有的拓扑规则要求：改动一条链路的下一跳之前，它必须先停用，并且相关服务器确认已没有任何会话（停止屏障）；停用的规则重新启用也同样要等服务器空闲。此外，拓扑校验不允许启用的规则指向已停用的下一跳。更新不放宽其中任何一条，因此**每次更新都会中断这条转发**。几组规则：

- **P（`stopped`）**：入口，以及最深变化层之上所有留下的规则。其中只有 **R（`rewired`）**，即下一跳发生变化的那些规则会改向。但 P 中的规则一路指向 R，启用的规则又不能指向已停用的规则，所以 P 整体先暂停、再一起停用，改向时再一起重新启用。被移除服务器上指向 P 的规则随 P 一起停用，之后不再启用。
- **`quiet`**：P 中留下的规则所在的服务器。停用和改向前，这些服务器必须**整机**空闲。被移除的服务器不在其中，离线或已经不在的被移除服务器不会挡住改向和更新的成功。例外是还原：见下文“还原等待哪些 Agent”。
- 新服务器上的规则一开始就启用并带着最终路由；改向之前没有规则指向它们，所以不停用、不等待。

**入口什么时候需要空闲：总是需要。** 只有第 1 层变化时，P 只有入口；第 2 层或更深的层变化时，P 还包括入口与该层之间留下的中转，例如第 2 层变化时是入口加上第 1 层的全部中转。入口服务器上其他规则的会话，同样会让更新等到截止时间并自动还原。

步骤：

1. `preparing`：先在新服务器上添加规则，等这些服务器的 Agent 确认应用，并且 `quiet` 中每台服务器在线、配置已同步。这一步不影响现有流量。
2. `draining`：暂停 P 中各条规则的全部目标（`paused_until_ms` 为截止时间），入口不再接受新连接，已有连接继续。**暂停有期限**：更新拖到截止时间时暂停先结束，此时如果已经停用，新连接会因规则已停用而失败，直到改向或还原。这属于预期的中断。
3. `stopping`：`quiet` 中的服务器**整机**空闲（任何规则都没有会话或探测，即 `topology::quiescent`）后，停用 P，再等停用被确认，且服务器仍然空闲。
4. 改向（`confirming`）：一个批次写入 R 的新下一跳，重新启用并恢复 P，停用被移除服务器的规则。控制器此时提交，但结果要等 `quiet` 中服务器（本次暂停和停止的服务器）的 Agent 都应用后才是 `succeeded`；之前 `interrupted` 为 true。被移除服务器停用旧规则、新服务器的规则不承载这条转发，它们的 Agent 只在 `agents` 里列出，不等待，所以已登记但离线或宕机的被移除服务器不会让更新受阻。有 Agent 拒绝，或到 max(截止时间, 改向后 60 秒) 仍未确认，就进入 `blocked`：`outcome` 为 `failed`，`failed_in` 为 `confirming`，并逐台写明哪台、什么错误。改向之后**只向前**：不自动撤回，被拒的 Agent 继续运行上一份已应用的配置并自动重试；全部确认后转为 `succeeded`，`notes` 保留“曾受阻”。`blocked` 时可以取消，含义是“不再等待确认”：配置保持改向后的样子，转交人工处理。
5. `cleanup`：被移除服务器的规则在其服务器空闲后删除，不影响转发。服务器长期离线时，按提示吊销并删除该服务器，更新随即不再等它。

### 截止时间、取消与还原

- 截止时间从确认时起算，默认 600 秒，可在 plan/refresh 请求中用 `timeout_secs` 调整，范围 60–86400。控制器重启后从原始开始时间继续计算，不重新计时。准备、暂停和停止各阶段每次推进都会先检查截止时间，过期就不再发布暂停或停止。这些接口与其他转发链写接口相同：需要可写角色，令牌需要 `nodes:write`。
- 改向之前，下列情况都会进入 `restoring`：取消、超时、任一步发布被拒、Agent 报告应用错误、发起人失去权限，以及别人改动了这条转发的规则（**包括只改名称**）。结果为 `failed` 或 `cancelled`，并记录 `failed_in`（停在哪一步）和 `error`。
- **还原不等待会话结束。** 本次停用的规则在路由与更新开始时记录的完全一致时，直接重新启用，即便服务器上还有其他规则的会话。依据：改向之前，路由图与更新前那张已通过校验的图相同（只少了新加的、无人指向的规则），不会成环，也不会把新旧路由的会话混在一起。这个豁免只在还原的发布里有效（`topology::prepare_with`，store 模块内可见），条件是：
  - 同一台服务器的这次更新只切换启用状态和暂停，不增删规则，也不改路由或监听；
  - 重新启用的规则的路由签名与记录相同。

  其余检查照常执行：修订、权限、端口、全图校验与防环、旧 Agent 能力门控。普通 API、批量发布、模板和共同规则在同样条件下仍返回 409。
- 还原在**一个事务**里读取当前配置、判断资格并发布，判断的是发布时刻的完整配置，不是更新开始时的快照。整批不能通过时，能通过的服务器先还原，其余显示为 `restore_blocked`：逐台原因列在 `waiting`（`retry_error` 是合在一起的文字），`interrupted` 保持为 true。只要各服务器的修订、应用错误或 Agent 报告的能力（`*_node:<id>` 记录）有变化就立即重试，否则每 30 秒重试一次，不再每 2 秒全量校验。例如：有人占用了已停用规则的监听端口，或者更新开始后规则所有者被加上了入口 Agent 不支持的上传限速。
- **下一跳保持停用的规则不重新启用。** 要重新启用的规则，如果它的某个下一跳仍是停用的（例如别人在停止后停用了留下的出口，或下一跳本身也留给人工处理），启用会被拓扑校验（启用的规则不能指向停用的下一跳）每次都拒绝。还原因此直接让它保持停用，列入 `unresolved`，写明先启用哪个下一跳；它上游的规则依此类推，其余照常恢复，更新正常结束，不会无限重试。
- 还原发布后进入 `restore_confirming`（面板“恢复配置已提交，等待 Agent 确认”）。**还原等待哪些 Agent：** `quiet` 中服务器的 Agent，以及被移除服务器中、还原重新启用其旧规则的那些：改向之前入口仍把流量分给它们（例如中转 2 离开第 1 层、加入第 3 层，还原把它在第 1 层的旧规则重新启用，入口按来源哈希把一部分客户端分给它）。这样的服务器只在它的 Agent 已应用本次的暂停或停止时才等待；从未应用的 Agent 一直运行原来的配置，还原本来就是那个样子。控制器每一轮（2 秒）看到它已应用，就把它记进更新记录（`carried`），之后即使它的 Agent 换了新租约重启（控制器会把它的已应用修订置 0），还原也照样等它确认；只有在应用后不到一轮就换租约时才会漏记。新服务器上被停用的新规则不等待。**Agent 迟到确认更早的停止不算确认还原。** 路径上的 Agent 报告应用失败时显示 `restore_failed`；提交 60 秒后仍未全部确认显示 `restore_overdue`。两者各写一次审计（`restore_rejected`、`restore_overdue`），逐台原因在 `waiting`，面板给出处理办法。在这些 Agent 都确认之前，转发不算恢复可用（`interrupted` 为 true）；之后照常继续，`notes` 记录“曾被拒绝或逾期”。
- **结束恢复。** `restoring` 阶段（`restoring`、`restore_blocked`、`restore_confirming`、`restore_failed`、`restore_overdue`）可以用取消接口结束：已发布的配置不变，也不再重试；本次停用而仍停用的规则、本次暂停而仍暂停的目标逐条列入 `unresolved`，写明原因和处理办法；新加的规则交给 `cleanup`，但仍启用的新加规则（它所在服务器的那部分还原被拒，没能停用）也列入 `unresolved`，写明是本次更新加的、仍带监听、转发不用它，待没有其他规则指向它后在服务器的规则中删除，不会被清理误记为“别人改过”。审计 `end_restore`（调用者）和 `restore_ended`（系统）。未确认的 Agent 会继续自行重试，它们应用之前 `interrupted` 仍为 true。结束后转发链可以删除，也可以开始新的更新。
- **Agent 降级与旧版 Agent。** 能力标记只写一次（0.150.0 的既有设计），控制器看不到降级：门控照常放行，更新照常发布带暂停目标等新字段的配置。规则和配置的格式拒绝未知字段，所以不认识新字段的旧 Agent 无法解析整个同步回复：它照常上报（控制器看到它在线、修订未应用），在本地日志写 `incomplete or invalid controller response; retaining local configuration`（错误为 `invalid controller JSON`，连续失败只写一次），继续用上一份已应用的配置转发，**不上报应用错误**，所以面板看不出原因是 Agent 太旧。验证线用真实 0.141.9 Agent 程序、沿用原状态目录实测了降级的入口：
  - 截止之前，暂停一直是 `pending`，`interrupted` 为 true，面板显示这条转发不接受新连接；而旧 Agent 实际照旧用旧配置转发，流量没有断。
  - 到截止时，还原配置不带它不认识的字段，它能解析并应用；更新以 `failed`（超时）结束，转发全程没有中断，**实测没有出现“待确认 → 逾期”**。
  - 风险：`timeout_secs` 设得越长，面板显示“中断”的时间就越长，而实际流量可能并没有断。
  - 处理办法：等到截止时间，或手动取消更新（**旧 Agent 上的取消路径没有实测**），然后把 Agent 升级到 0.145.0 或更高。
  - 只有还原配置本身也带它不认识的字段（例如规则的限速）时，还原才无法应用，提交 60 秒后显示 `restore_overdue`，`waiting` 写明在等哪个修订；这时服务器在更新之前就已停在降级前的配置上。这一情形依据代码（`agent.rs` 的同步处理、`model.rs` 的 `deny_unknown_fields`），没有实测。处理办法同上，或去掉导致不兼容的设置，或“结束恢复”交给人工。

  只有 Agent 能解析配置、但应用时拒绝（例如端口被占用）才显示为 `failed` / `restore_failed`。服务器不再使用时，可以吊销并删除它。
- 新加的规则在还原时只停用，路由不变，屏障本就允许；删除放到 `cleanup`，按正常屏障等服务器空闲。
- 还原和清理以系统身份 `chain-refresh` 执行。

### 所有权：还原改什么、不改什么

还原只改本次更新仍“拥有”的字段：

- 本次停用的规则的 `enabled`；
- 本次暂停的目标的暂停状态；
- 本次新加的规则的 `enabled`。

所有权按**每一次写入**判断，而不是只比较最终值。从本次更新的暂停或停止提交起，逐个检查 `config_history` 中每个外部修订：只要它与前一个修订相比改动过上述字段，这个字段就归对方所有。例如有人先启用、再停用：最终值和更新写的一样，但所有权已经转移，还原不会重新启用，并在 `notes` 中说明。"是不是更新自己的写入"按 `commits[].revisions` 的修订号判断，不看用户：自动更新以开启者身份发布，开启者本人的手动修改仍算外部写入。历史中缺修订时，按所有权已转移处理并列入 `unresolved`。其他字段（名称、限速、来源列表，以及维护排空写的 `draining` 等）一律保持当前值。

- **在规则编辑里再保存一次"停用"，不能让规则保持停用**：这样的保存没有改动任何字段，还原仍会按所有权重新启用，并在 `notes` 写明"有人保存过该服务器，保存不能表达保持停用；如需停用请再次停用"。要保持停止，请用"取消并保持停止"（`POST …/refresh/cancel {"keep_stopped": true}`）。
- `keep_stopped` 只在改向之前（`preparing`/`draining`/`stopping`）接受，并要求调用者对每台会保持停止的服务器有写权限；只读角色或令牌返回 403（来自写权限检查）。逐台服务器的检查是**防御性检查，没有测试覆盖**：规则、服务器和转发链的租户在创建时绑定且不能修改，只有直接改数据库或恢复出不一致的数据库时才会触发，经 API 无法构造。改向或还原发布之后返回 409，提示用普通方式停用规则。它只影响本次停用的规则；本次设的暂停照常恢复，新加的规则照常停用。这些规则列入 `unresolved`，写一条 `cancel_keep_stopped` 审计（带调用者），并说明以后怎样重新启用：用普通方式，需要服务器空闲。
- 路径上有规则被别人改了路由或监听、或被删除时，不使用豁免：本次停用的规则保持停用，逐条列入 `unresolved`，写明是哪条规则、为什么不能自动恢复、确认路由后怎样手动启用（需要服务器空闲）。本次设的暂停照常恢复，新加的规则照常停用。
- 更新开始前就已停用的规则（例如被移除服务器上、运维先停用的规则）不会被重新启用。

`interrupted` 反映这条转发的实际状态：本次停用的规则仍停用、本次暂停的目标仍暂停，或承载转发的服务器上的 Agent 还没应用最近一次暂停、停止、改向或还原，都算中断。承载转发的服务器与还原等待的服务器相同：`quiet`，以及改向之前、还原会重新启用其旧规则且已应用暂停或停止的被移除服务器；清理只在服务器的 Agent 已应用最新修订后才在它上面提交（`quiescent` 的条件），所以不会掩盖未应用的还原。结束后只看留给人工处理（`unresolved`）且仍停用的规则。

### 预览与确认

`POST …/refresh/plan` 不写任何数据，返回：`changes`（各层增减的服务器）、`conflicts`（存在时不能确认）、`warnings`、`notes`、`interrupts`、`timeout_secs`、`idle_servers`（每台必须空闲的服务器的在线、修订、应用错误、TCP/UDP 会话数和探测数，以及现在是否空闲，会话数包含其他规则）、`hops`（新服务器上的规则及连接地址）、`expected_revisions`、`result`（每台服务器更新并清理后与现在相比的逐条规则差异）、`preview`（第一步发布的配置预览）和 `token`。

冲突包括：层数变化、组或成员服务器已删除、入口服务器进入了某一层、入口或保留的规则被删除或已停用、规则被人工改为不再指向仍在下一层的服务器、使用了更新不支持复制的功能（端口段、受管协议网关、节点间 WS/WSS/TLS/PROXY/多路径等）、链外规则指向将要停止的规则、超过 64 台服务器、端口分配失败、更新后的拓扑无效、发布检查拒绝（例如新服务器的 Agent 太旧，不支持复制来的限速等功能）、转发链已停用、留下的下一跳没有公布的端点（新服务器无法指向它）。警告：下一层的来源列表或防火墙规则集不会随成员变化而修改，需人工确认新服务器是否被放行；`quiet` 中的服务器还承载其他转发的启用规则时，那些规则的会话可能一直挡住更新直到截止时间（自动更新视为冲突，不会开始）。

**旧 Agent 门控。** 比 0.142.0 更老的 Agent 不认识暂停的目标，会拒绝整份配置；同步协议里没有 Agent 版本号，也没有“支持暂停”的上报。控制器因此用一个保守的代理信号：反向隧道能力记录 `reverse_tunnel_node:<服务器 id>`。依据：0.145.0 起的 Agent 在控制器下发 `reverse_tunnels` 时（本版本控制器每次同步都下发）于每次同步的统计里带上 `reverse_tunnel`，其中 `managed` 恒为 true，与服务器配置无关；控制器第一次看到时写入记录，只有删除服务器才会清除。预览和确认都检查要暂停的服务器（`quiet`，总含入口）和新服务器：没有该记录时返回 409 并在 `lines` 逐台说明这台服务器上更新要做什么（暂停目标或添加规则），从未连接面板的提示“尚未连接，Agent（0.145.0 或更高）须先连上”，连接过的提示“Agent 还没报告能接受暂停的目标：太旧（请升级到 0.145.0 或更高），或刚刚连上（等它下一次同步）后重新预览”，此时没有任何暂停或停止。新服务器也检查，是因为更新要等它的 Agent 确认应用新规则。自动更新把连接过而没有该记录的服务器算作冲突，不会开始，并计一次失败；从未连接的服务器（例如先加进组、还没装 Agent）只让自动更新等待，不计失败，5 分钟后再看，`last_result` 以 `waiting:` 开头。从未连接的服务器连上之后，自动更新不会马上开始，而是等到原定的下一次检查（`next_attempt_ms`，最多约 5 分钟），之后照常进行（验证线实测）；想立即更新可以手动预览并确认。代价与限制：0.142.0–0.144.x 实际能暂停，也被要求升级；Agent 连上后的第一次同步还没有这项上报，要等它的下一次同步（验证线用真实 0.150.0 Agent 实测：第一次预览 409“尚未连接”，267 毫秒后写入记录，274 毫秒时预览通过）；记录只写一次，Agent 降级后控制器看不到（见上文）。被移除的服务器不检查：它的 Agent 太旧时只是一直运行旧配置，改向后它的规则不承载转发。

`POST …/refresh` 提交 `{token, expected_revisions, timeout_secs?}`。任何服务器修订变化返回 409 并在 `lines` 列出服务器；转发链、组或转发变化导致 `token` 不同、已是最新、存在冲突也返回 409。用同一 `token` 重复提交返回同一次更新，不会重复执行；更新进行中再发起另一次更新或删除转发链返回 409；另一条转发正在进行、且会暂停或停止的服务器与本次重叠时返回 409（两次更新不会互相等待对方的服务器空闲）。

### 控制器提交与 Agent 确认

每一步都是一次 `publish_in` 事务（与其他发布相同的修订、端口、权限、防火墙和旧 Agent 能力检查），提交后写入 `commits:[{step, at_ms, revisions}]`。`agents` 列出每台服务器最近一步的修订及 Agent 状态：`applied`、`pending`、`failed`（Agent 拒绝并继续运行上一份已应用配置）或 `not_enrolled`。下一步只在需要的 Agent 都确认后才开始；`waiting` 说明正在等什么。`stage` 给出面向人的阶段：`updating`、`confirming`（改向已提交，等 Agent）、`blocked`、`restoring`、`restore_blocked`（控制器拒绝部分还原，正在重试）、`restore_confirming`（还原已提交，等 Agent）、`restore_failed`（路径上的 Agent 拒绝还原）、`restore_overdue`（还原未按时确认）、`cleanup`、`finished`。控制器提交不等于转发已恢复可用；被跳过的冲突不算恢复成功。面板上的“x/y 台服务器的 Agent 已确认”只统计最近一次提交，并写明是哪一步、涉及哪些服务器（例如还原整批被拒时，计数是“停止规则”那次提交的；部分服务器先还原时，是只含这些服务器的“恢复原转发”提交，被拒的服务器另列在等待原因里）。

控制器的更新任务每 2 秒推进一次，每条记录单独处理：一条记录读取或推进出错只记日志，不影响其他转发；自动更新和清理已完成记录出错也只记日志，不拖慢这一轮的还原和截止；整轮出错或 panic 也不退出循环，连续失败 n 次后多等 n 个间隔（最多 30 个），成功一次即恢复每个间隔推进。

### 自动更新

自动更新默认关闭，只能对单条转发显式开启（`PUT …/sync {auto_sync:true, timeout_secs?}`）。开启后，组成员变化时控制器以开启者身份发起与手动确认相同的更新，因此**每次自动更新同样会中断这条转发**，也同样受截止时间和还原约束。预览中的冲突、`quiet` 中的服务器还承载其他转发的启用规则，或相关服务器的 Agent 连接过却不能暂停目标（见“旧 Agent 门控”），都会让自动更新不开始，并计一次失败；相关服务器从未连接时只等待，不计失败（5 分钟后再看，面板单独显示在等哪台服务器和下次检查时间；它连上之后，自动更新也要等到这次检查才开始）；这样等待不会清零之前的失败次数，之前的失败仍计入“连续 3 次关闭”，而一次等待会把原本更长的退避（例如 20 分钟）换成 5 分钟；另一次更新还在进行、或转发链已停用时只是等待，不计失败。每次运行前都重新检查开启者：用户被删除、停用或失去写权限时自动关闭并记录在 `auto_sync_stopped`，不沿用旧权限。无法开始或失败的自动更新按 5 分钟起、每次加倍退避（`next_attempt_ms`），连续 3 次未成功后自动关闭。审计动作：`forwarding_chain.refresh`（开始、每一步发布、取消和结束）、`forwarding_chain.auto_sync`（开启、关闭、自动停止）和 `forwarding_chain.auto_sync_failure`。

### 存储

不新增数据库表。更新记录在 metadata `chain_refresh:<入口规则 id>`（最近一次），自动更新设置在 `chain_use:<入口规则 id>` 的 `auto_sync` 和 `auto_sync_stopped` 字段中。每一步在一个事务中发布并记录下一步，控制器重启后从记录的步骤继续。

## 删除

- **删除服务器**：不受端点组和使用记录阻止（仍受其他规则 `via` 引用等原有检查约束）。端点组中该成员显示为已删除（`missing`），保存端点组时需将其移除；在此之前不能用包含它的转发链新建转发（409）。使用记录中对应的规则显示为已缺失。
- **删除端点组**：只删除记录，服务器和规则不受影响；仍被转发链使用时返回 409。
- **删除转发链**：删除转发链记录和它的使用记录，用它建成的规则全部保留为普通规则。修改转发链时，入口规则已不存在的使用记录被一并遗忘。
- **删除建成的转发**：与其他多跳转发相同，在“全部转发”中删除。

| GET | `/api/v1/endpoint-groups` | 可见的端点组：`[{id, tenant_id, name, description, members:[{node_id, node_name, missing}], used_by:[{id, name}], created_at_ms, updated_at_ms}]` |

| DELETE | `/api/v1/endpoint-groups/{id}` | `{ok:true}`；被转发链使用时 409 |
| GET | `/api/v1/chains` | 可见的转发链：`[{id, tenant_id, name, enabled, layers:[{group_id, group_name, balance, members:[{node_id, node_name, missing}]}], uses:[{entry_rule_id, entry_node_id, entry_node_name, name, missing, layers:[[{node_id, rule_id, node_name, missing}]], out_of_date, changes:[{layer, added, removed}], auto_sync\|null, auto_sync_stopped\|null, refresh\|null}], created_at_ms, updated_at_ms}]`；`auto_sync` 为 `{enabled_by, enabled_at_ms, timeout_secs, failures, next_attempt_ms, last_result?}`，`refresh` 为当前或最近一次更新 `{id, automatic, actor_id, started_at_ms, deadline_ms, updated_at_ms, phase, stage, outcome, cancel_requested, failed_in, error, retry_error, problems, notes, changes, interrupted, waiting, servers, agents, retire_pending, unresolved:[{node_id, rule_id, error}], commits}` |

| DELETE | `/api/v1/chains/{id}` | `{ok:true}`；规则保留 |
| POST | `/api/v1/chains/{id}/plan` | `{entry_node_id, name, protocol, target, entry_port\|null, owner_id?}` → `{entry_rule_id, hops, batch, preview}`；不写任何数据 |
| POST | `/api/v1/chains/{id}/apply` | 同上，可加 `expected_revisions` → `{entry_rule_id, hops, published}`；一个批次，全部成功或全部不变 |
| POST | `/api/v1/chains/{id}/uses/{entry_rule_id}/refresh/plan` | `{timeout_secs?}` → 更新预览；不写任何数据 |

## 面板

「转发规则」的“全部转发”页面下方、“共同规则”之后是“端点组与转发链”区块：

- **端点组**：“＋ 新建端点组”填写组名称、说明和“成员服务器（按顺序）”，可“上移”“下移”“移除”和“添加服务器”。列表显示成员（已删除的服务器标为“服务器已删除”）和“使用此组的转发链”，以及“编辑”“删除”。
- **转发链**：“＋ 新建转发链”填写转发链名称、“启用：可以用此链创建新的转发”，并逐层选择“第 N 层 · 端点组”和“上一跳在这一层中的选择方式”，可“＋ 添加层”“移除此层”。列表显示各层的组、候选服务器和选择方式，“用此链创建的转发”（已过期的标为“组成员已变化”，并列出各层新增和移除的服务器），以及“用此链新建转发”“编辑”“删除”。
- **更新转发**：已过期的转发有“预览更新…”：对话框说明更新会中断这条转发和最长用时，列出必须空闲的服务器（在线、已同步、TCP / UDP 会话、现在空闲）、新服务器及连接地址、冲突、警告和逐条规则的“查看更新前后配置”；有冲突时不能确认，否则可修改“最长用时”后“确认更新”。进行中的更新显示阶段、等待原因、“最近一次提交‘某一步’（涉及的服务器）：控制器已提交；x/y 台服务器的 Agent 已确认”及未确认或应用失败的服务器，改向之前可“取消更新”或“取消并保持停止…”，受阻时可“不再等待确认…”，恢复中可“结束恢复…”；还会显示受阻、恢复受阻（控制器拒绝，逐台原因）、恢复配置已提交（等待 Agent 确认）、恢复受阻（Agent 无法应用）和恢复逾期的阶段，说明恢复配置提交不等于转发已恢复可用并给出处理办法，以及需要人工处理的规则和处理方法。更新进行中提示：在规则编辑里再保存一次“停用”不会保持停止。预览还说明暂停可能先于更新结束。自动更新在等待从未连接的服务器时，单独显示“自动更新在等待，不计为失败”、下次检查时间和原因，之前的失败另起一行只显示次数。每条转发可“开启自动更新…”（确认框说明每次都会中断转发、以开启者身份执行及自动关闭条件）或“关闭自动更新”。
- **新建转发**：“＋ 新建转发”的选择页中有“按已保存的转发链 → 使用已保存的转发链”。表单选择转发链、入口服务器（只列出转发链租户中链外的服务器）、转发名称、传输协议、最终目标和可选的入口端口，并以表格列出各层候选。“预览发布内容”调用 plan，用与引导式新建转发相同的预览页显示整条路径图和逐台变更；“发布这些变更”调用 apply 并带上预览时的修订号。
- “全部转发”中由转发链建成的转发显示“转发链 · 名称”，已过期时另显示“组成员已变化”。

## 验证与限制

- `crates/relay-platform/tests/chains.rs` 36 项集成测试：
  - `plan_builds_every_layer_towards_every_server_of_the_next_layer`：入口、第 1 层 2 台（来源 IP 哈希）、第 2 层 3 台（最少连接）的不对称转发链，核对每条规则的目标、`via`、地址和均衡方式、按转发设置分配的端点（含跳过已占用端口与指定入口端口）、已有规则保留，以及规划不写数据；
  - `apply_publishes_every_server_in_one_batch_and_records_the_use`：一个批次发布 6 台、发布后的边、使用记录、第二次新建取下一个空闲端口、删除转发链保留规则；
  - `a_failure_on_one_server_publishes_nothing`：入口端口被占用、最后一层端口范围已满、规划后某台服务器修订变化，三种失败都不修改任何服务器且指出出错的服务器；
  - `chains_groups_and_entries_are_validated`：服务器在两层、入口在链内、组成员数量与重复、无效目标和端口、修改组导致重叠、删除被使用的组、停用的转发链、最低延迟的连接探测与 UDP 拒绝、层数上限、跨租户的组和入口、删除成员服务器；
  - `a_use_is_out_of_date_after_its_groups_change`：组成员增减后报告已过期及变化、只调整顺序不算、删除入口服务器后显示已缺失；
  - `tenants_are_isolated_and_viewers_cannot_change_chains`：租户隔离（404）和只读用户 403；
  - `the_api_plans_and_applies_a_chain_with_token_scopes`：HTTP 接口的规划、应用、逐服务器 409、只有 `read` 的令牌可读不可规划而 `nodes:write` 可以、删除被使用的组 409，以及更新的开启自动更新、预览、确认、过期预览 409 和取消；入口从未上报时第一次预览 409、`lines` 只指出入口；取消照面板的方式发送（JSON 类型头、空请求体）成功，之后显示 `restore_confirming`、仍算中断，入口确认后结束；只含空白字符的请求体同样按没有请求体处理（更新已结束，返回“不能再取消”的 409）；JSON 语法错误 400、未知字段 422；
  - `a_refresh_rewires_member_changes_and_keeps_manual_edits`：修改组本身不改动任何服务器；预览列出必须空闲的入口；新服务器复制同层规则的设置；确认只发布新规则且重复确认返回同一次更新；新 Agent 应用前不暂停；任何规则的会话都使其保持排空；停用确认后才改向；改向后等全部 Agent 确认才算成功；人工修改保留；被移除服务器的规则在空闲后删除；逐步核对审计及执行身份；
  - `a_refresh_below_the_first_layer_stops_everything_above_it_together`：第 2 层加服务器时入口和第 1 层一起暂停、停用、改向后重新启用，新服务器接上；三层链中被移除且事先已停用的规则在还原后保持停用；中转从第 1 层移到第 3 层时，同一台服务器上既有被停用的旧规则又有新加的规则，还原时它仍有会话，旧规则照样按原路由重新启用、新规则只停用，空闲后由清理删除；
  - `a_restore_that_cannot_complete_is_shown_and_can_be_ended`：还原提交后入口 Agent 报告失败显示 `restore_failed`、错误消失但仍未应用显示 `restore_overdue`、确认后继续并写说明；没有错误也未确认时提交满 60 秒才显示逾期且只审计一次，操作者结束后已发布配置不变、Agent 应用前仍算中断；监听端口被占用时 `restore_blocked` 逐台列出原因，保持停止在这一阶段 409，结束后入口列入 `unresolved` 并写明原因，之后不再重试；停止后有人停用了留下的出口时，中转和入口直接留给人工处理并写明先启用哪个下一跳，暂停恢复、更新结束而不是无限重试；
  - `servers_off_the_path_do_not_hold_a_refresh`：已登记但不再上报的被移除中转不挡改向确认，更新成功，只有清理等它，另一次更新可以开始并接着清理；已登记但不应用的新服务器使更新在准备阶段等到截止，还原停用它的新规则也不等它，之后可以删除转发链；
  - `a_refresh_that_cannot_finish_puts_the_forwarding_back`：排空中取消立即恢复并删除新规则；停用后某台服务器一直有其他会话，到截止时间不等空闲即以原路由重新启用；截止时间从确认起算；Agent 无法应用暂停（如旧 Agent）时结束并恢复；截止时间已到而没有任何等待时，不再发布暂停或停止，直接结束；
  - `offline_servers_and_old_agents_keep_the_forwarding_running`：已登记但从未上报的离线服务器在预览中显示为离线、不空闲，使更新停在准备阶段、到期不中断即放弃；新服务器 Agent 太旧不支持复制的限速时预览指出且不发布；
  - `a_refresh_refuses_conflicts_stale_previews_and_changes_by_others`：过期预览（修订或组变化）、人工改向、链外规则指向将停止的规则、停用的转发、层数变化、权限与租户、进行中再次更新或删除转发链、别人修改规则后结束且不覆盖、新服务器无 Agent 时等待；
  - `automatic_refresh_is_opt_in_backs_off_and_stops_without_permission`：自动更新默认关闭；开启后以开启者身份执行到底；无法开始时退避并在 3 次后关闭；开启者被停用后自动关闭而不沿用旧权限；
  - `a_refresh_continues_after_a_restart_with_its_original_deadline`：在停止、还原确认、清理、暂停和改向确认阶段重启后继续推进；截止前一刻不还原、到原截止时刻还原；
  - `a_restore_puts_back_only_what_the_refresh_still_owns`：改名加同值保存后重新启用且保留名称并写说明；别人先启用再停用后不再启用、也不改向；别人启用时保持启用；维护排空保留；暂停之后改名同样还原；别人改名了更新新加的规则时，还原只停用它，清理不删除并写说明；
  - `cancelling_can_keep_the_stopped_rules_stopped`：只读用户 403；保持停止列入 `unresolved` 并写审计；普通方式启用在服务器有会话时仍 409；改向后保持停止或取消返回 409；停止的规则所在服务器已被吊销并删除时，保持停止不因它返回 404；
  - `a_restore_is_checked_against_the_configuration_it_publishes_into`：链外和同服务器其他规则的变化不影响还原；迟到的停止确认不算还原确认；监听端口被占用时还原受阻并重试，解除后完成；路径上规则换了监听时入口保持停止并逐条说明；
  - `a_gate_that_applies_since_the_start_blocks_the_restore_until_resolved`：更新开始后才生效的上传限速门控在入口挡住还原，显示 `restore_blocked`，Agent 报告支持后完成；
  - `a_refused_restore_is_retried_on_a_change_or_after_30_seconds`：还原被拒后，取消规则所有者的限速（不改任何服务器的修订，不在立即重试的条件内）时，29 秒内不重试、仍为 `restore_blocked`，满 30 秒重试并完成；
  - `ordinary_publishes_still_wait_for_an_idle_server_during_a_refresh`：更新进行中，配置接口、批量发布、模板在同样条件下仍 409（停止屏障）；共同规则占用入口端口在更早的端口检查就 409，另外用一条经 `via` 指向中转、参与拓扑的共同规则在忙碌的入口服务器上先停用再启用，启用碰到同一个停止屏障 409；
  - `after_the_rewire_a_refresh_only_goes_forward`：Agent 拒绝改向时 `blocked`、不撤回、之后确认转为成功并保留说明；未按时确认时 `blocked`，操作者可不再等待；改向确认中删除转发链 409，提示写明“Agent 拒绝改向时，或到更新的截止时间”才能结束；
  - `apply_errors_refused_steps_and_lost_permission_put_the_forwarding_back`：新服务器 Agent 无法应用、入口 Agent 无法应用停止、确认后链外规则指向中转使停止被拒、发起人停止后被停用，都还原；
  - `refreshes_that_share_servers_do_not_run_together`：共用服务器时预览警告；另一条转发的更新进行中再确认 409；自动更新等待不计失败，之后因共用服务器不开始并计失败；
  - `chains_and_removed_servers_can_be_deleted_after_a_refresh`：清理期间删除转发链后记录在完成时被遗忘；更新后可删除被移除的服务器；
  - `the_refresh_task_goes_on_past_a_record_it_cannot_read`：存在无法读取的记录时，更新任务照常把另一条正在还原的更新推进到完成，且不退出；
  - `chain` 的单元测试 `the_refresh_loop_survives_failures_and_panics_and_backs_off`：更新任务的循环在出错、panic 后继续，连续失败时每次多等一个间隔、最多 31 个，成功一次即恢复；
  - `automatic_refresh_runs_and_fails_like_a_confirmed_one`：手动更新进行中不启动自动更新；自动更新超时还原、自身提交不算外部写入、计失败并退避；开启者本人先启用再停用也按外部写入处理；停用的转发链只暂停；开启者被删除后自动关闭；
  - `a_next_hop_without_an_endpoint_is_a_conflict_not_a_failure`：留下的下一跳没有公布端点时，租户管理员的预览和自动更新都只报冲突，之后其他租户的请求照常完成（锁未被毒化）；
  - `agents_that_cannot_pause_targets_are_refused_before_anything_changes`：按 0.141.9、0.144.0 和 0.150.0 各自 `SyncRequest`/`EngineStats` 的真实 JSON 形状上报：入口为 0.141.9 或 0.144.0 时预览和确认都 409、提示升级到 0.145.0、只指出入口，任何服务器的修订不变、没有暂停也没有更新记录；入口为 0.150.0 时通过；预览拒绝的文字写明这台服务器上更新要做什么（入口“pauses targets on”、新服务器“adds rules to”）并带统一前缀；从未上报的新服务器提示“尚未连接”，自动更新为它等待、不计失败，5 分钟后它按 0.144.0 连上时计一次失败；新服务器按 0.150.0 上报后照常开始；第 2 层变化时，第 1 层要暂停的中转按 0.144.0 上报也 409，只指出这台中转；
  - `a_restore_waits_for_removed_servers_it_enables_again`：入口 → [1, 2] → [3] → [4]，中转 2 离开第 1 层、加入第 3 层：中转 2 应用了停止、之后不应用还原时，状态为 `restore_confirming`、`waiting` 列出它、仍算中断，60 秒后 `restore_overdue`、`outcome` 为 `failed`，它报告应用错误时 `restore_failed`，确认后才进入清理且不再中断；在中转 2 应用还原前结束恢复，仍算中断，清理也等它应用还原后才删除它上面新加的规则；中转 2 应用停止后、还原前它的 Agent 换了新租约（真实的释放与获取租约，控制器把已应用修订置 0），还原照样等它，并显示新进程的拒绝；走完改向时不等中转 2，路径上的 Agent 应用改向后，中转 2 被停用的旧规则不算中断；中转 2 从未应用暂停或停止时，还原不等它；
  - `ending_a_restore_lists_an_added_rule_it_could_not_disable`：有人让另一台服务器的规则指向本次新加的规则，还原在新服务器上被拒（`restore_blocked`），结束恢复后这条仍启用的新规则列入 `unresolved`，写明是本次更新加的、需在没有规则指向后删除，`notes` 不把它记成“别人改过”；
  - `automatic_refresh_errors_do_not_hold_up_other_refreshes`：存在一条格式损坏的端点组记录、自动更新整轮出错时，另一条更新照常在截止时间还原，这一轮不报错；
  - `real_agents_keep_open_sessions_and_switch_to_the_new_relay`：环回上的控制器、更新任务和三个真实 Agent：把一层从中转 A 换成中转 B，排空期间已打开的会话继续、新连接被拒绝，会话结束后完成改向，新连接经中转 B；
  - `real_agents_get_the_forwarding_back_when_another_session_outlasts_the_deadline`：同样的环回环境，入口服务器上另一条规则的长连接在停止之后一直不断：改向被挡住，到截止时自动还原，新连接经中转 A 恢复，那条长连接不受影响，中转 B 上新加的规则被删除；那条长连接每 250 毫秒收发一次，全程没有一次失败。截止时间由测试直接推进，不实际等待 60 秒。
  - `on_the_wall_clock_the_refresh_task_puts_the_forwarding_back_by_itself`：同一场景，但控制器的更新任务照生产方式运行：测试先把更新推进到停止阶段、打开那条长连接并等它被上报，然后才启动更新任务，此后不再推进任何一步，按真实时间等 60 秒（允许的最短截止时间）：截止前 2 秒仍在停止阶段，截止后 5 秒内由任务自行还原，新连接经中转 A 恢复，长连接全程收发不断（至少 150 次）。这个测试约需 61 秒。任务之所以后启动：先启动的话，CPU 繁忙时任务可能在长连接打开前就看到入口空闲而改向（这是正确行为），测试会偶发失败。
- `store::topology` 的单元测试 `only_enabling_a_stopped_rule_with_its_old_route_skips_the_idle_check`：只有路由与记录一致、同服务器只切换启用状态时才跳过空闲检查；路由不同、同一次更新改路由、新增或删除规则（包括删除不参与拓扑的规则）、其他服务器的键都仍 409；只读角色 403；空集合与原检查相同；豁免下仍做全图校验：下一跳被停用时，在忙碌的服务器上用豁免启用、在空闲的服务器上不用豁免启用，都因“指向停用的下一跳”被拒绝。
- `scripts/test_web_chains.cjs` 在中英文下运行面板代码，核对端点组和转发链的新建、编辑、删除，“使用已保存的转发链”的 plan 与 apply 发送的请求，以及更新的预览内容（中断说明、必须空闲的服务器、冲突时不能确认）、确认请求、进行中和失败的状态显示、取消与“取消并保持停止”、受阻、恢复受阻、恢复配置已提交但 Agent 拒绝或逾期的阶段（不显示为等待确认）、计数写明是哪一次提交、结束恢复发送的请求、需要人工处理的规则、不再等待确认，以及开启自动更新前的确认，自动更新在等待从未连接的服务器时与之前的失败分开显示、不当作失败原因。
- 保存成功只表示期望配置已提交；各服务器是否已应用、防火墙是否放行所示端口、路径是否可达，仍需在“节点应用状态”和客户端确认。
- 不支持：节点间 WS / WSS / TLS / PROXY / 多路径、受管协议网关、端口段、最终目标多于一个。最后一层到最终目标固定为加权轮询。
- 更新的限制：每次更新（包括自动更新）都会中断这条转发，从暂停到改向不接受新连接；入口和最深变化层之上的中转所在服务器以整机计必须空闲，其他规则的会话也会阻止改向直至截止时自动还原（还原不等空闲）；暂停在截止时结束，之后到还原前新连接失败；暂停的结束时间按 Agent 自己的时钟；门控拦不住已降级的 Agent：它不上报错误，暂停一直显示为待确认、面板显示中断，而它实际照旧转发，到截止时应用还原，更新以超时失败结束（见上文“Agent 降级与旧版 Agent”，验证线用真实 0.141.9 实测）；不能暂停目标、从未上报过该能力的旧 Agent 由门控在预览和确认时拒绝（代理信号要求 0.145.0 或更高，0.142.0–0.144.x 也要升级；对旧版本的拒绝只按旧版同步格式的夹具测试，没有用真实旧版程序实测）（`offline_servers_and_old_agents_keep_the_forwarding_running` 用模拟 Agent 上报错误，覆盖的是能解析、应用时拒绝的情况）；共同规则只能经自己的线路碰到停止屏障，碰不到本次更新停用的规则；没有安装 Agent 的服务器按空闲计；下一层的来源列表和防火墙规则集不自动修改；层数变化需新建转发。真实 Agent 只在环回上测试过；与旧版本 Agent 程序的混合只实测了上面的 0.141.9 降级。
- 验证线的独立验收（真实进程、0.150.0 Agent、生产 2 秒推进）覆盖了门控、截止自动还原、逾期后自动完成、`restore_failed`/`restore_overdue` 不显示为已恢复、换租约后仍等被移除的服务器、自动更新等待从未连接的服务器。未测：被移除的服务器在控制器的同一轮之内应用停止并换租约、拿到新租约后到还原前一直不同步的组合（没有凑出来；集成测试只覆盖控制器至少看到过一次已应用的情况）；清理已完成记录（`forget_orphans`）出错时不影响其他更新的隔离。
