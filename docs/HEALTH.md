# 目标健康与优先级选择

0.10.0 为每个规则增加可选的主动探测，并为目标增加 `priority` 和 `max_sessions`。不开启探测的旧规则保持原来的拨号选择方式。SQLite schema v4 和恢复日志格式保持不变；控制器和 Agent 应协调升级，再发布新字段。旧 Agent 不接受这些字段。

## 配置与成功条件

以下字段加入现有规则。`tcp` 和 `udp` 必须恰好覆盖规则协议；`both` 必须同时提供两者。探测请求要适合重复执行，不能使用会创建订单、修改数据等有副作用的业务请求。

```json
{
  "health_check": {
    "interval_ms": 1000,
    "timeout_ms": 1000,
    "unhealthy_threshold": 2,
    "healthy_threshold": 2,
    "recovery_delay_ms": 5000,
    "max_age_ms": 10000,
    "tcp": {
      "kind": "exchange",
      "request_base64": "UElORw==",
      "expected_base64": "UE9ORw==",
      "half_close": false
    },
    "udp": {
      "request_base64": "UElORw==",
      "expected_base64": "UE9ORw=="
    }
  }
}
```

此例要求服务收到 `PING` 后回复 `PONG`，普通回显服务应把 expected 改成 `UElORw==`。可运行的回显示例见 [health-echo.json](../examples/health-echo.json)。

TCP 支持两种检查：

- `{"kind":"connect"}`：完成目标 TCP 连接和配置中的 PROXY、TLS、WS 建链步骤。它不证明业务已回复，也不应单独作为服务端已接受客户端证书的最终证明。
- `exchange`：发送请求、刷出数据，读取并精确匹配预期字节前缀；`half_close:true` 在发完请求后关闭写方向，仍等待回复。TCP 请求可以为空，用于等待欢迎消息；响应前缀必须非空。更长的后续响应不参与此检查。

UDP 必须发送非空请求并收到一个完整、精确匹配的响应包；仅成功创建 UDP socket 不算健康。连接的目标地址限制收包来源。同一目标在探测成功期间复用同一个 UDP socket（同一来源端口），目标是下游中转时只占用对方一个 UDP 会话；任何一次失败或超时后换用新 socket，发送前丢弃上一次探测之后才到达的回包。若回包比超时还晚、恰好在下一次探测期间到达，仍可能被算作那一次的响应。响应超过 1024 字节不可能与配置的预期内容匹配。TCP 和 UDP 独立维护状态，TCP 故障不会直接摘除同一目标的 UDP。

请求和预期响应采用标准 Base64，解码后各最多 1024 字节。没有通用 HTTP 状态码、正则或 JSON 路径解析器；HTTP 服务可以配置可重复的原始请求和响应前缀，但不要将前缀匹配等同于完整 HTTP 校验。

| 字段 | 缺省值 | 范围 / 含义 |
| --- | ---: | --- |
| interval_ms | 1000 | 100～300000；每个端点的期望间隔 |
| timeout_ms | 1000 | 25～60000，且不超过间隔；覆盖 DNS、连接、握手和收发全过程 |
| unhealthy_threshold | 2 | 1～20；连续失败达到阈值后摘除 |
| healthy_threshold | 2 | 1～20；首次接纳与恢复前需连续成功 |
| recovery_delay_ms | 5000 | 0～600000；恢复阈值达到后仍须持续成功的观察时间 |
| max_age_ms | 10000 | 至少 interval + timeout，最多 3600000；结果失效时间 |

0.19.0 起缺省值从 5000/2000/3/2/5000/20000 调整为上表数值：目标拒绝连接时约 0.25～1.25 秒摘除，不回应时约 2～3 秒（旧缺省约 15～17 秒）；已稳定健康的近距离目标见下文“自适应探测超时”，约 0.5～1.5 秒。缺省时每个端点每秒一次探测。摘除依靠连续失败，结果有效期 10 秒只在探测本身停止时起作用；控制台显示的年龄还包含节点上次回报以来的时间（缺省轮询 5 秒），有效期短于“探测间隔 + 回报间隔”会让正常目标在控制台显示为过期。已保存的规则带有完整字段，升级不会改变它们的数值；只有省略字段的新配置使用新缺省值。

## 状态与业务行为

新规则、需要重建的探测配置和 Agent 重启从 `unknown` 开始。达到成功阈值后才允许新业务；未知、故障、恢复观察或过期的目标不会作为“兜底”被强制使用。探测开始后、首次接纳之前不等待 recovery delay，即使其间探测失败过（例如多跳链路中下一跳还在启动）；recovery delay 只用于曾经接纳、随后故障的目标。首次接纳之前，以及健康目标出现失败、尚未达到摘除阈值期间，探测间隔为 `interval_ms` 的四分之一（不少于 100 ms，不超过 `interval_ms`），其余时间为 `interval_ms`；已摘除的目标按正常间隔探测。缺省设置下新规则、Agent 重启后的目标约 0.25 秒即可接纳；目标第一次探测失败后约 0.25 秒（加上探测超时）即可完成第二次判断。目标不回应时，摘除时间主要由每次探测的等待时间决定。

**自适应探测超时**：健康且最近窗口内已有至少 5 次成功的目标，每次探测最多等待“窗口内最慢一次成功耗时的 2 倍”，不少于 250 ms，不超过 `timeout_ms`。往返 3 ms 的目标等 250 ms，偶尔要 400 ms 才回复的服务等 800 ms，远距离或慢服务仍按 `timeout_ms`。第一次失败后用于确认的第二次探测仍使用这一较短限制；已摘除、恢复观察中、尚未接纳的目标使用完整 `timeout_ms`，让变慢但仍可用的路径能够恢复。缺省设置下，近距离目标突然不回应时约 0.5～1.5 秒摘除（集成测试：1 秒间隔、1 秒超时的 UDP 目标，固定超时实测 3.0 秒，自适应后低于 1.8 秒）。代价是：耗时突然超过近期最慢值 2 倍并连续两次的路径会被暂时摘除，恢复要经过成功阈值与 recovery delay。

健康目标达到连续失败阈值后变为 `unhealthy`。再次达到成功阈值后进入 `recovering`，还要在 recovery delay 内保持连续成功。期间任何失败都会重置恢复过程。年龄超过 max age 立即按 `stale` 排除；后续单次成功不会绕过恢复阈值和观察期。Agent 使用单调时钟判断年龄，不依赖控制器时钟决定转发。

新 TCP 连接和新 UDP 会话只在可用目标中选择。全部不可用时拒绝新业务，不缓存并重放业务数据。已经建立的 TCP 不因目标健康变化而主动迁移或断开，仍遵守原有空闲、到期、安全策略和配置生命周期。UDP 目标变为不可用或探测被撤销时，该会话退出；下一次新到达的数据包可建立新会话，已经发送的包不会自动重放。系统报告目标端口不可达（目标进程退出时收到 ICMP 端口不可达，表现为发送或接收被拒绝）时，会话立即退出，并把该目标排到其他目标之后 10 秒（与 TCP 建链失败相同，目标仍可作为最后选择），所以下一个数据包无需等待健康探测即改走其他目标；不配置健康探测的规则同样生效。主机整机无回应时没有这个信号，仍由探测超时决定。

新 TCP 连接不等待探测也会绕开故障目标：一次真实连接在某个目标上失败（DNS 失败、拒绝、超时或建链步骤失败）后，该目标在 10 秒内排到其余可用目标之后，仍可作为最后的候选。这一被动降级只调整顺序，不改变探测状态、统计或报告；无探测的规则同样生效。

建链采用竞速：某个目标在“对冲延迟”内还没连上时，不放弃它，同时拨下一个候选，先连上的胜出，其余尝试关闭。对冲延迟为该目标探测延迟的 4 倍、至少 250 ms；没有探测数据时为 1 秒；且不晚于按剩余候选平均分配 `connect_timeout_ms` 的份额。所有尝试共用一次 `connect_timeout_ms` 截止时间。目标明确失败时立即拨下一个。竞速落败（只是慢、未失败）的目标：配置了健康探测时不降级，由探测判断，所以偶发丢失一次握手回包不会让正常主线路被冷落 10 秒；无探测的规则把它当作失败降级 10 秒。

恢复后，新连接和新 UDP 会话可回到更高优先级目标；仍健康的已有 UDP 会话继续保持目标亲和性。应用自行重发、会话切换时的在途 UDP 丢包都不提供恰好一次保证。

## 优先级、权重与容量

每个 target 可配置 `priority`（0～65535，缺省 0）和 `max_sessions`（可选，1～1000000）。数字越小越优先；在最低可用优先级池中执行现有加权轮询、来源哈希或加权最少连接策略。拨号失败时继续尝试其他可用目标，包括更高数值的后备目标。同优先级仍使用 `weight`，优先级不会取代权重。

0.19.0 新增 `"balance":"lowest_latency"`：在最高可用优先级池中，按探测耗时从低到高选择目标，尚无耗时样本的目标排在最后。选路用的耗时是最近 5 次成功探测的中位数：偶发的一两次慢回复不影响选择，持续 3 次的变化即生效（缺省 1 秒间隔约 3 秒）。控制台显示的 EWMA 只用于展示。当前选中的目标只有在另一个目标比它快超过 10% 加 1 ms 时才会被替换，避免测量抖动让新连接来回切换。此模式必须配置健康探测，否则发布被拒绝。`exchange` 探测会穿过下游中转一直到达最终服务，因此测得的是整条后续链路的往返耗时；`connect` 探测只覆盖到下一跳的建链。耗时为节点到目标的探测往返，不是客户端看到的完整延迟；选路只影响新连接和新 UDP 会话，已建立的连接不迁移。旧版 Agent 不认识此取值，会拒绝该配置并保留原版本，应先升级 Agent 再使用。

### 丢包与抖动

每个端点保留最近 20 次探测结果。健康报告新增 `window_checks`（窗口内探测次数，最多 20）、`window_failures`（其中失败次数，包括超时和回复不符）和 `jitter_us`（窗口内相邻两次成功探测耗时之差的平均绝对值；中间夹着失败的两次不配对；不足两次相邻成功时为 `null`）。

`lowest_latency` 排序使用“最近 5 次成功耗时的中位数 + 窗口失败率 × 1 秒”。1 秒是 TCP 初始重传超时（RFC 6298 第 2.1 节）：丢失的 SYN 或 SYN-ACK 会让建链多等这么久，所以 20 次里失败 1 次的目标多计 50 ms。这样，连续失败不足摘除阈值、仍算“健康”的丢包路径会排在干净但稍慢的路径之后。抖动只用于显示，不参与排序。

其他分配方式（加权轮询、来源哈希、最少连接）不按耗时排序，但会避开丢包目标：窗口内失败至少 2 次且至少占 10% 的可用目标视为“丢包降级”（报告 `selection_reason` 为 `degraded`，`eligible` 仍为 true）。同一优先级还有未降级的目标时，只在未降级目标之间分配，降级目标排在其后作为备用；同一优先级全部降级时照常分配。优先级不受影响：降级的主目标仍排在更低优先级的后备之前。失败移出 20 次窗口后自动解除。窗口按探测次数而不是时间计，缺省间隔下约为最近 20 秒；健康状态的摘除与恢复规则不变。新字段和 `degraded` 原因由新版 Agent 上报，旧控制器会拒收含 `degraded` 的整份健康报告，所以控制器必须先升级（与 0.19.0 遥测相同）。

目标容量为**本 Agent、同一规则、同一目标地址字符串**的活跃 TCP 连接与 UDP 会话之和，并由该规则的整个端口段共享。并发接纳使用原子预留；旧连接仍在时，目标删除后重新加入不能凭此清空占用。容量变小不会赶走已有连接，只限制新接纳。它不是所有节点的全局容量，也不会合并不同 DNS 别名或不同规则。

固定端口映射的多个入口共享同一目标观测；偏移映射按每个目标端口分别检查。每个 Agent 最多 256 个启用的“规则 × 目标 × 映射端口 × 协议”探测点，最多 16 个并发探测。繁忙时等待并跳过错过的周期，不无限补发。端点较多且超时较长时，实际间隔可变长并导致结果过期，应据此调整间隔和有效期。

仅修改名称、权重、优先级或容量，可保留相同路径的已有观测；路径、探测策略、到期时间或证书材料变化会重建观测。新配置准备失败时旧配置和旧探测继续运行。停用规则会取消探测；拓扑改向的停止确认同时要求 active TCP、UDP 和探测数归零，范围仍是整节点。

## 路径、计量与凭据

探测复用实际业务的目标解析、DNS 缓存、出口 IP/网卡绑定、节点内环路检查，以及目标 PROXY/TLS/mTLS/WS 参数。对带 `via` 的目标，应用请求可以穿过其后实际链路；成功只证明本次探测所走路径的回复，不能证明下游每个并列候选都可用。

源节点主动探测不经过自己的业务入口、不占业务目标会话容量、业务配额或业务速率桶。探测应用字节单独统计；TLS、PROXY 和 WS 封装不计入这些应用字节。这里是有资源上限的诊断流量，不是业务账本。如果探测经过另一个受管转发规则，下游按实际收到的应用负载正常计量、限额和限速，可能影响该节点的剩余额度。

启用出口 PROXY 时，主动探测声明的是源节点实际出站 socket 地址和被探测目标地址，没有伪装成某个业务用户。下游来源 ACL 必须允许这一来源。私钥仍仅在节点本地；健康 API 返回错误分类，不回传探测响应体或 TLS 私钥路径。

## API 与页面

`GET /api/v1/nodes/{id}/health` 使用用户身份认证，遵守节点租户可见性，只读用户可访问自己可见节点。返回实际/期望修订、应用错误、最后心跳、上报的活跃探测数、预期端点数量、规则名称和 `reports`。没有报告不表示健康。

每条报告包含规则、目标下标、入口映射端口、协议、目标地址、`probe_kind`、`status`、`eligible`、`selection_reason`、年龄/有效期、节点记录时间、成功延迟 EWMA、连续成功/失败、完成/成功次数、错误分类、探测应用字节和目标容量。EWMA 只纳入成功样本，权重为旧值 7/8 + 新值 1/8，测量 DNS 至预期响应的总时间；失败不产生新的成功时延。

`eligible:true` 表示健康、未满且未到期，可参与选择；`selection_reason:standby` 仍可能 eligible，表示当前存在更优先的池。此信息是采样时的候选状态，不保证稍后连接一定被接纳。活跃数也是节点最后一次上报的采样，不是控制器实时读取 socket。

Agent 在同步 stats 中上报 `active_probes` 和 `target_health`；旧请求省略时按零/空解析。控制器按该节点**实际应用修订**验证端点归属、协议、地址、策略和边界，拒绝无效报告时同批用量也不提交。诊断报告不作为计费或配额退款依据。

控制器读取时将距最后回报的时间加到结果年龄；超过有效期显示 stale 且不可用，不修改保存的原始样本。这个显示依赖控制器时钟和心跳新鲜度；不会向 Agent 下发一个“健康授权”。Agent 本地探测在控制链路短暂中断时继续进行。

管理界面新增“目标健康”页、规则探测编辑器和目标优先级/容量字段，每 5 秒刷新。源码与语法已检查，浏览器视觉和点击验收仍待完成。

## 验证与后续范围

`tests/health.rs` 覆盖真实 TCP/UDP 故障、恢复观察、已有会话、容量跨配置保持、端口映射、并发上限、重启、报告归属/新鲜度，以及 mTLS WSS + PROXY 下的端到端探测与下游计量。控制 API 测试从发布到真实 Agent 验证健康状态和独立用量；拓扑测试确认取消探测后才允许改向。

```sh
python3 scripts/check_health.py --output docs/health-smoke.json
```

该脚本运行独立 Python 业务服务与 Release 控制器/Agent，检查主备切换、TCP/UDP 独立性、恢复、全部失败、同一 UDP 客户端失效后的重建，以及旧备份重放后的配置和用量。交替测量两条规则的普通/健康选择开销；两者共用 Agent，后台探测在两组期间均运行，因此不是关闭所有探测后的资源消耗对照。

具体通过项、二进制与原始样本见 [VALIDATION.md](VALIDATION.md)。成本权重、延迟自适应调度、跨节点容量租约、完整路径质量评估、被动失败反馈、告警历史与全部 22 个模块继续保留，未以本功能替代。
