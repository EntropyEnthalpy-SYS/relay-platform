# 单连接多路径流传输

本平台独立实现的协议名为 relay-multipath-v1。它在多条经过双向 TLS 认证的 TCP 子流上传输一条有序双向字节流，支持分片、复制、方向选择、固定窗口、故障重传和半关闭。控制 API、规则历史、备份、节点配置及编辑器使用同一份规则模型。

这不是 Linux 内核 MPTCP，也没有宣称与 Hammer 或其他产品专有协议互通。[RFC 8684](https://www.rfc-editor.org/rfc/rfc8684.html)描述内核 MPTCP 的序列映射、子流与连接级确认；这里使用独立应用协议，没有实现该 RFC 的 TCP 选项、地址管理或耦合拥塞控制。

## 部署和选择

普通 TCP 应用连接发起端；发起端为每个目标建立一条子流；同一汇聚规则重组后只连接一次后端。路径数为 1～8，一条目标对应一条子流，不能把候选后端服务器当作汇聚端。没有业务数据跨连接重放；全部可用方向失效时终止当前业务连接。

- 发起端配置 outbound_multipath；汇聚端配置 inbound_multipath，并要求 inbound_tls.client_ca。所有发起目标使用相同 TLS 服务名、CA 和客户端身份。私钥留在各节点本地目录。
- 每条路径的实际网络连接可独立指定 outbound_bind，未指定时继承规则绑定；IP 或网卡绑定失败会拒绝应用配置/建立连接，不会悄悄改为无绑定。DNS 查询继续使用系统路由。
- 支持 TLS 内嵌 PROXY、TLS 前 PROXY 和 WSS 组合。ACL 仍逐条检查实际连接；使用 PROXY 时还检查声明的来源，加入同组的原始地址元数据必须一致。组身份始终来自验证后的 TLS 客户端证书。
- inbound_multipath 可以与 outbound_multipath 同时出现，实现当前节点先汇聚再建立下一组。各跳独立接纳计量。
- 端口映射必须为 fixed，TCP-only。一个汇聚规则可以监听端口段；声明式拓扑允许其前驱引用同一规则的不同段内端口。原有多租户隔离、环路检查和结构变更排空屏障继续适用。
- 若配置 via，全部子流必须引用同一汇聚规则，不能将已知受管端点改为无引用外部目标绕过校验。不同 DNS/NAT 别名仍不能被控制器自动识别。
- 端口不同不保证物理链路或带宽独立。实际多 WAN 需要节点网络和路由提供相应路径；当前配置不会自动修改系统策略路由。

本机示例见 [multipath-hop.json](../examples/multipath-hop.json)。它展示同一进程的两个规则及两个子流端口，不代表两条独立网络。准备与 [README 的业务 TLS](../README.md#业务-tls) 相同格式的 root、client、server 配置目录，后端在 19100 监听，业务客户端连接 19101。实际跨节点部署时拆分两条规则，替换地址和主体 ID，并配置同租户的下一跳引用。

## 配置合同

limits 的字段两端相同，发送及接收的窗口帧数协商取较小值；重传和停滞时间分别使用各端本地策略。

| 字段 | 默认值 | 范围 / 行为 |
| --- | ---: | --- |
| window_frames | 64 | 4～256；一帧最多 16 KiB；FIN 也占用一个序号 |
| max_sessions | 64 | 1～1024；包括建立中的会话；超限立即拒绝 |
| retransmit_ms | 500 | 50～10000 ms；超时重传等待的下限，实际等待按实测往返时间计算（见下文） |
| stall_timeout_ms | 30000 | 1000～120000 ms，至少为重传间隔的四倍 |
| inbound.max_paths | 4 | 1～8；同一会话不能重复使用槽位 |
| inbound.allow_replication | false | 是否接受复制模式 |
| outbound.mode | stripe | stripe 或 replicate |
| outbound.min_paths | 必填 | 建立时成功子流最少数；运行中允许降级，只要上下行仍各有可用路径 |
| outbound.paths | 必填 | 与 targets 按位置一一对应，最多 8 项 |
| paths[].upload_weight | 必填 | 0～1000；0 禁止该路径承载上行应用数据 |
| paths[].download_weight | 必填 | 0～1000；0 禁止该路径承载下行应用数据 |
| paths[].outbound_bind | 继承规则 | 可选 ip / interface；任一子流至少启用一个方向 |

两个方向必须各有至少一个可用路径。普通目标优先级必须为 0；实际子流数据调度使用方向权重。普通目标的 max_sessions 约束物理子流。入站 max_connections 也约束物理连接；聚合逻辑会话另受 limits.max_sessions 约束。

stripe 在有效子流中优先选择“仍未确认的已分派负载 / 方向权重”较小的路径，平局轮换。首选发送队列短暂满时等待它继续，避免任务调度顺序掩盖权重；满队列持续一个重传超时后排除它，允许其他可写路径前进。重传仍优先选择不同的可写路径。确认和可写性反馈会影响分配；权重不承诺精确的最终字节比例，也不是按实时 RTT/吞吐预测的自适应调度器。

replicate 将每一帧排入所有当前有效方向的子流；队列均有空位后才继续分派该帧，慢路径可限制吞吐。正常半关闭等待已排入的发送完成，故障/取消时仍可能存在部分发送；故障重传独立统计。

建立总期限沿用 connect_timeout_ms。其中 80% 用于候选连接与认证加入，预留 20% 完成开始屏障。CREATE 只发起一次，结果不明时不尝试另一个汇聚后端。开始屏障后不再加入、重建或替换子流；当前连接内的断路恢复依靠剩余路径重传。自动补建是后续扩展。

修改聚合策略、证书材料或原有安全策略会取消关联会话。非安全元数据变更复用现有组注册表与会话限额。停用、停机和配置排空会等待驱动及子流退出；有聚合会话/子流残留时，控制器不将节点视为排空，也不提前按业务空闲归还预算。

## 序列、确认和失败边界

两个发送方向分别从帧序号 0 开始，DATA 和 FIN 各消耗一个序号。接收端按序写入有界应用缓冲，再发送累计 ACK。ACK 指下一期望序号；它确认传输层缓冲交付，不确认后端应用事务，也不替代持久化账本。

发送端仅保留累计确认边界之后的窗口帧。ACK 可携带 256 位选择确认，说明窗口内哪些帧已收到；这只释放路径调度占用并停止重复重传，不能释放发送保留窗口或提前交付应用。收到累计 ACK 后才释放旧帧；出现子流 I/O 错误时让受影响的未确认帧立即具备重传资格；超时重传尽量选择不同的可写子流。重复帧不再次向应用交付，乱序帧不得超过当前窗口。窗口内同序号不同内容、非法帧类型、错误 FIN、超过窗口、超大长度和不存在的发送确认都会导致失败。

超时重传等待按子流分别计算（RFC 6298）：该子流的平滑往返时间加四倍偏差，不低于 retransmit_ms，不高于 stall_timeout_ms 的四分之一。按 Karn 规则，重传过的帧不提供往返样本；复制模式各副本同时发出，最先到达的确认作为各副本所在子流的样本。某子流每次超时重传把它的等待时间加倍（每个超时周期最多一次，最多 64 倍），拿到新样本后恢复。这样往返时间长于 retransmit_ms 或比其他子流慢的链路不会把未丢失的帧复制到其他子流；I/O 失败的路径上的帧仍立即重传，不计为超时。

静默失效的子流（例如中途被防火墙单向丢包）仍可能长时间接受写入操作系统缓冲，看起来可写；反方向甚至可能继续送达对端的帧数秒，所以收到对端的帧不能证明本端的帧能送达。只发往某一子流的帧超时后，该子流被标记为可疑：等待它的一个重传超时（随失败加倍），期间 stripe 的新帧和重传在还有其他子流时都避开它；之后一次只试发一个新帧，直到某个只经它发送的帧被确认，才恢复正常分配。重传副本只发往可信子流。复制模式不受影响。

没有确认进展且存在未确认帧时，超过 stall_timeout_ms 中止。单次子流写/刷新也有该期限。普通业务空闲/到期继续由规则限制。对方应用不读取时，有界应用缓冲和窗口形成背压。

ACK 广播到活跃子流，重复 ACK 可合并到最新值；控制帧和数据发送公平轮换就绪机会，避免连续确认更新饿死数据。已有接收进展时每半个重传间隔补发确认，恢复累计 ACK 丢失，即使所有帧已经选择确认也不会永久占住窗口。远端 FIN 的应用 EOF 在相关 ACK 刷新后才可见；本地 shutdown 等待 FIN 确认和已排队发送完成。传输损坏或路径全部失败报告错误，不能伪装成正常 EOF。

单个聚合会话每个方向最多有 window_frames 帧在途，吞吐上限约为 window_frames × 16 KiB ÷ 往返时间。例如往返 184 ms 时，默认 64 帧约 45 Mbit/s，256 帧约 180 Mbit/s。长距离链路需要更高吞吐时调大 window_frames，并按下文内存边界确认节点内存足够。

## 内存边界

一个已建立会话的发送保留窗口最多 W×16 KiB，接收重排窗口也最多 W×16 KiB；窗口按帧数限制，短帧也占槽位，不能利用短帧产生无上限的条目数量。

额外缓冲仍有硬上限：双向应用桥各 64 KiB、最多 32 个入站事件、每条子流一个正在解析的帧、每条子流一个发送中帧和一个排队帧、一个本地读取缓冲。共享引用不会因复制路径数直接复制窗口内容；转换和 I/O 中的临时帧也需计入实际内存。保守负载存储估算为 2×W×16 KiB + (32+4×P+1)×16 KiB + 128 KiB，其中 P≤8。这不包含条目/任务元数据、TLS/WSS 自身缓冲和内核网络缓冲，不是进程 RSS 上限。

配置校验要求单侧规则的 2×W×16 KiB×max_sessions 不能超过 256 MiB；一个节点所有启用聚合规则两侧的该值之和不能超过 512 MiB。这是配置中的发送/重排窗口预留上限，不包含上述额外开销；安全策略变更时旧驱动异步取消，旧缓冲与新配置可能短暂重叠，不能将配置预留数当作瞬时 RSS 硬上限。健康探测由节点级 16 个探测并发限制，每个聚合探测固定使用 4 帧窗口。

## 计量与观测

业务配额和应用限速位于重组后的逻辑流上；分片报头、ACK、FIN、同组重复帧不再次作为业务接纳量。一个包含两跳的平台链路仍在两条规则各计一次上下行。接纳后发送失败可能已经计费，沿用原有合同。

源节点健康探测通过一条真实认证聚合子流检查目标；源探测应用量单列，下游汇聚规则收到的探测应用负载正常计量。探测的聚合连接会进入进程级传输诊断。

EngineStats.multipath 与节点运行诊断展示：

- active_sessions / active_paths、累计 sessions、failed_paths；
- sent_payload_bytes 为实际写入外层传输的帧负载，包括初次发送、复制、重传；失败写可能只完成部分；
- replicated_payload_bytes 和 retransmitted_payload_bytes 是上述总量中的额外副本部分，两者不互相包含；
- received_payload_bytes 统计完整读取帧的负载，duplicate_payload_bytes 统计去重丢弃部分，delivered_payload_bytes 为按序写入应用桥的负载；
- framing_sent_bytes 为实际写入的 16 字节帧头及 ACK 选择确认位图，不含建立握手；
- peak_reorder_bytes / peak_send_window_bytes 为单个会话达到的最大窗口占用，跨会话取最大，不能当作节点总内存；
- path_sent_payload_bytes 为 8 个配置槽位的实际发送负载，在本次进程的所有规则间累加；不是按链路名称持久化的历史统计。

这些诊断计数从进程启动累计、非事务快照，重启归零。它们不含 TLS、WebSocket、TCP/IP 报头或内核重传，不是网卡账单。复制会增加真实线路开销，当前业务配额/速率不能作为网卡带宽硬上限。

新 Agent 会发送 multipath 诊断字段，旧控制器拒绝未知字段，因此升级顺序为控制器先、Agent 后。旧 Agent 不识别聚合配置；必须先升级再发布相应规则。数据库 schema 仍为 4。

## 公开线格式 v1

所有整数为大端，无隐式字节对齐。外层按已有顺序处理可选 PROXY、必须的 mTLS、可选 WSS；WSS 仍使用 relay-stream-v1 子协议，其应用字节才是以下帧。不得使用未认证的普通 TCP 承载本协议。

首次 CREATE 和后续 JOIN 均为固定 84 字节：

| 偏移 | 长度 | 值 |
| ---: | ---: | --- |
| 0 | 8 | ASCII RLYMP001 |
| 8 | 1 | CREATE=1，JOIN=2 |
| 9 | 1 | 子流槽位 0～7 |
| 10 | 1 | stripe=0，replicate=1 |
| 11 | 1 | 保留，必须为 0 |
| 12 | 2 | 窗口帧数 |
| 14 | 2 | 上行权重 |
| 16 | 2 | 下行权重 |
| 18 | 2 | 保留，必须为 0 |
| 20 | 32 | 客户端随机 session ID，不能全零 |
| 52 | 32 | CREATE 时全零；JOIN 时为服务器返回的随机 token |

服务器成功回复固定 42 字节：ASCII RLYMPA01（8）、协商窗口（2）、随机 token（32）。注册键绑定验证过的客户端叶证书 SHA256 和 session ID；JOIN 还须匹配 token、模式、窗口及适用的 PROXY 原始地址。token 只在加密连接内交换，不进入控制配置或日志。

完成全部成功加入后，发起端在 CREATE 所用子流发送 ASCII RLYMPS01（8）和成功槽位位图（1）。位图必须包含原始子流且只能包含已注册槽位。汇聚端收齐对应子流、确认两个方向存在后回复 ASCII RLYMPOK1（8），然后双方进入帧阶段。此时才交给普通后端转发逻辑，后端连接失败将终止聚合流。

后续固定 16 字节帧头：

| 偏移 | 长度 | 值 |
| ---: | ---: | --- |
| 0 | 1 | DATA=1，FIN=2，ACK=3 |
| 1 | 3 | 保留，必须为 0 |
| 4 | 8 | 帧序号，或 ACK 的下一期望序号 |
| 12 | 4 | 长度：DATA 为 1～16384；FIN 为 0；ACK 为 0 或 32 |
| 16 | 长度 | DATA 原始负载；ACK 可选 32 字节选择确认位图 |

ACK 不消耗序号。长度 0 仅表示累计确认；长度 32 时，位图第 i/8 个字节的低位起第 i%8 位表示序号 ACK.sequence+i 已接收（i=0～255）。超出协商窗口或未发送序号的置位拒绝。当前原生端发送 32 字节位图，也接受只支持累计确认的端点。没有重连恢复、UDP 帧、流复用、压缩或格式协商；未知版本/字段拒绝，不静默降级。握手错误关闭当前连接，非法业务帧中止该组。传输 I/O 错误可仅移除受影响子流。

## 验收边界

自动测试覆盖窗口、断路重传、复制去重、半关闭、非法帧、真实 mTLS/WSS、证书绑定、方向选择、权限/拓扑继承、容量、健康探测和策略取消。受控单连接基准脚本为 scripts/bench_multipath.py，最新结果以 VALIDATION.md 中链接的实测文件为准。

Linux 实机、多 WAN、不同 RTT/丢包、长期高负载、自动补建子流、按规则/路径持续存储的观测、独立服务端实现互通及与原产品兼容仍需各自验收。Python/OpenSSL 客户端线格式检查仅证明文档列出的入站组合。浏览器视觉与点击没有验收；源码和语法通过不等于界面实测。
