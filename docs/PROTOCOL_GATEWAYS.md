# Managed protocol gateways (development 0.115.0)

The optional gateway adapter connects VLESS (TLS or Reality, with optional Vision), Hysteria2, TUIC v5, AnyTLS, Trojan and VMess to the native rule engine. Protocol wire handling uses **sing-box 1.14.4** as a separate process. It is an upstream component, not an independently written implementation of those protocols.

## Installation and source ownership

`third_party/sing-box/` contains the unmodified corresponding source archive, upstream license notice, GPL v3 text and a pinned checksum manifest. The archive includes upstream `go.mod` and `go.sum`. Go dependency source is resolved during a source build; the archive is not a fully vendored, offline build environment. Upstream licensing and naming/association restrictions remain applicable.

Stage a verified engine package into a new directory:

```sh
python3 scripts/stage_protocol_engine.py --directory ./engine-package --target linux-amd64
```

The command verifies the pinned binary archive and bundled source SHA-256 values. It does not change services. `linux-arm64` and `darwin-arm64` archives are also pinned. To use an already downloaded archive, add `--archive /path/to/archive.tar.gz`. Do not omit source and license files when redistributing the engine.

Install the staged binary at an absolute path readable/executable by the agent, such as `/usr/local/lib/relay-engines/sing-box-1.14.4`, owned by the operator and not writable by group or others. Set `RELAY_PROTOCOL_ENGINE` in the agent environment. Symlink binaries and other engine versions are rejected. The existing deployment installer also accepts agent settings `protocol_engine` and `tls_directory`; these paths remain local operator settings, never controller-supplied executable paths.

To build from the bundled upstream source, use its required Go version (1.25.5 or newer, as stated in `go.mod`), extract the source and run:

```sh
CGO_ENABLED=0 go build -trimpath \
  -tags "$(cat release/DEFAULT_BUILD_TAGS_OTHERS)" \
  -ldflags "-X github.com/sagernet/sing-box/constant.Version=1.14.4 -s -w -buildid=" \
  -o sing-box ./cmd/sing-box
```

This build command pins the version instead of using the upstream Makefile's latest-tag discovery. Byte-for-byte reproducibility of an upstream release binary has not been established.

## Panel workflow

1. Provision a node-local TLS identity as described in the TLS section of `README.md`, or choose VLESS/Reality and specify a handshake server you are authorized to use.
2. Add a rule and select the protocol in the gateway section. The main listen address is the client-facing address. Generate a UUID/password as appropriate. Reality has a separate private-key generator.
3. Set payload TCP or TCP+UDP, sources, destinations, ports, quota, rate, expiry and connection/session bounds. AnyTLS currently accepts TCP payloads only. Private destinations default to denied. For Reality, allow the camouflage server's address/port in destination policy too; its handshake and fallback bytes consume the same budget.
4. Publish and verify the node's applied revision. Node diagnostics report engine version, running state and automatic restarts.
5. Create a client subscription. sing-box JSON and mihomo/Clash Meta YAML carry every gateway; Surge, V2Ray and Shadowrocket carry the protocols those clients support (see [Client subscriptions](SUBSCRIPTIONS.md#受管协议入口)). For wildcard listeners, supply the public host. Certificate server name can differ from the host clients dial. Client certificate verification stays enabled. Install a private CA or pin its certificate in the client if using privately issued certificates.

Surge skips VLESS/Reality, and V2Ray and Shadowrocket skip AnyTLS, with explicit preview reasons. Single rules can also be shared as a link and QR code; see [Share links and QR codes](#share-links-and-qr-codes). A sing-box export contains outbounds and routing; add the local SOCKS/TUN inlet appropriate for the client application. Client exports contain protocol client credentials and Reality **public** keys, never Reality private keys, local TLS keys or private bridge credentials. Subscription links must be protected as credentials.

## Protocol options

These options are optional. Their defaults are today's behaviour and are left out of the stored rule, so configurations that do not use them are byte-for-byte what earlier agents accept. A rule that uses one is rejected by agents that predate it (rule fields deny unknown names): upgrade the agents before using the options. Every option name and value below was checked against the bundled sing-box 1.14.4 source (`option/hysteria2.go`, `option/tuic.go`, `option/tls.go`, `common/tls/reality_server.go`).

| Rule field | Values | Engine inbound | sing-box client export | mihomo export |
| --- | --- | --- | --- | --- |
| Hysteria2 `obfs` | `{"type":"salamander","password":…}`, password 16..256 bytes | `obfs` (same object) | `obfs` (same object) | `obfs: salamander`, `obfs-password` |
| Hysteria2 `masquerade` | `{"type":"string","status_code":200..599,"content":…}`, content up to 4096 bytes | `masquerade` `string` type | — (server only) | — |
| TUIC `congestion_control` | `bbr` (default), `cubic`, `new_reno` | `congestion_control` | `congestion_control` | `congestion-controller` |
| TUIC `zero_rtt_handshake` | `false` (default), `true` | `zero_rtt_handshake` | `zero_rtt_handshake` | `reduce-rtt` |
| Reality `extra_short_ids` | up to 15 more short IDs, 2..16 hex digits each, unique ignoring case | `reality.short_id` list: `short_id` first, then these | `reality.short_id`: the first only | `reality-opts.short-id`: the first only |
| Reality `max_time_difference_secs` | 1..3600; unset leaves the check off | `reality.max_time_difference` as a duration (`"90s"`) | — (server only) | — |

- Clients need the same obfuscation password; without it they cannot connect. Salamander is the only obfuscation offered; the engine's `gecko` type needs packet-size settings Relay does not expose.
- The masquerade answers HTTP/3 requests that fail authentication; without it the engine answers 404. Only the engine's fixed `string` response is offered. Its `file` masquerade would serve node files, and its `proxy` masquerade dials from the engine directly, outside the metered bridge, the destination ACL and the budgets, which would let a rule owner reach node-local services. Both are rejected.
- 0-RTT makes reconnects faster, but early data can be replayed by an on-path attacker. It stays off unless chosen.
- Additional Reality short IDs let groups of clients use different IDs, so one can be withdrawn without changing the others. Exports and share links always carry `short_id`, the first one. A clock limit rejects clients whose clock differs from the node's by more than the limit; keep node clocks synchronized before setting it.

The panel's gateway section shows these fields for the selected protocol; Reality short IDs are entered comma-separated, the first one going to clients.

## Share links and QR codes

`GET /api/v1/nodes/{node}/rules/{rule}/share?host=…[&port=…][&name=…]` returns `{"uri":…,"qr_svg":…}` for a gateway rule. `host` is the address clients dial (required; wildcard listeners have no public address). `port` defaults to the gateway listener's port and `name` (up to 120 bytes) to the rule name. Whoever may read the node's configuration may read its links; other tenants get 404. The panel's rule list has a 分享链接 / Share link action for gateway rules that shows the link and its QR code.

| Protocol | Link |
| --- | --- |
| VLESS | `vless://UUID@host:port?encryption=none&type=tcp[&flow=xtls-rprx-vision]&security=tls&sni=…`; Reality: `security=reality&sni=…&fp=chrome&pbk=PUBLIC_KEY&sid=SHORT_ID` |
| VMess | `vmess://` + Base64 of the v2rayN JSON: `v=2`, `ps`, `add`, `port`, `id`, `aid=0`, `scy=auto`, `net=tcp`, `type=none`, `tls=tls`, `sni` |
| Trojan | `trojan://PASSWORD@host:port?security=tls&sni=…&type=tcp` |
| Hysteria2 | `hysteria2://PASSWORD@host:port/?sni=…[&obfs=salamander&obfs-password=…]` |
| TUIC | `tuic://UUID:PASSWORD@host:port?sni=…&alpn=h3&congestion_control=…` |
| AnyTLS | no widely used scheme: 409; use a subscription |

Credentials, query values and the `#name` fragment are percent-encoded. A link carries the same client material as the subscription export: never the Reality private key, local TLS keys or bridge credentials. It cannot say that certificate mode needs a privately issued CA trusted (no `insecure` flag is ever written), that UDP is disabled, or that TUIC uses 0-RTT (there is no common parameter); clients use their default, 0-RTT off, which still connects. The QR code is rendered by the controller and holds the same secret as the link.

## Enforcement and lifecycle

- One shared engine process handles up to 64 enabled gateway rules on a node. No engine process starts for native-only configurations.
- Each gateway routes exclusively to a native, loopback-only SOCKS bridge with a random credential per applied generation. There is no engine direct-egress fallback for authenticated business traffic.
- The Agent owns each gateway's public listener; the engine listens on a loopback port of its own choosing per start. Before any byte reaches the engine, the Agent judges the client's own address (the kernel's peer address; IPv4-mapped addresses as IPv4) by the rule's expiry, the server's and the rule's inbound firewall rule sets ([FIREWALL.md](FIREWALL.md)) and the rule's source CIDR lists. The native engine applies destination ACLs, private-address policy, rule/owner/tenant/node budgets, aggregate rates, execution gating and durable payload accounting on the bridge, as before.
- Accounting measures admitted application bytes in each direction, excluding outer TLS/QUIC/protocol framing. **Reality has an explicit exception:** its camouflage handshake/fallback connection also traverses the authenticated native bridge. Its opaque TLS bytes consume the same rule/owner/tenant/node budgets and rates, and destination/private-address restrictions apply. This closes an otherwise unmetered direct-egress path, including unauthenticated fallback traffic. Allow that destination explicitly when using an allowlist.
- Source checks happen before the protocol engine: a refused TCP client is reset when accepted, nothing it sent is read, and the engine never starts a TLS handshake or a Reality camouflage connection for it (the kernel still completes the TCP handshake). Every UDP datagram (Hysteria2, TUIC) is judged as it arrives; refused datagrams are dropped in the Agent and never reach QUIC. A rule-set edit holds an open QUIC association at its next datagram either way: a client it refuses gets none of the engine's datagrams after that, and its association ends. A client whose address or port changes is a new association, judged afresh. Open TCP connections are judged once, when they open, as for native rules. Refusals go to the block records (protocol `gateway`, the client's own address). Spoofed UDP source addresses cannot be told apart, and local processes can reach the engine's loopback port directly — the same trust boundary as the loopback bridge. These checks are not a host firewall.
- The public listener only passes bytes on; it neither meters nor throttles. `max_connections` and `udp_max_sessions` keep their meaning: they count the connections and UDP sessions clients open through a gateway, once, on the bridge; a client's own TCP or QUIC connection counts against neither. What clients hold on the public listener is bounded, so that no client, or flood of them, starves the others or the Agent: per gateway at most 4,096 client TCP connections and 4,096 client UDP associations, or `max_connections` and `udp_max_sessions` when higher; per source (an IPv4 address, or an IPv6 /64) at most 256 connections and 64 associations (a client that holds a larger IPv6 prefix, such as a /56 with 256 /64s, counts as many sources, so the per-gateway bound is what holds it); and for every gateway together at most half of the Agent's open-file limit in descriptors (two per connection, one per association), leaving the rest of the Agent room to work. These are resource bounds, not session limits users see; a client over one is refused with `connection_limit` or `udp_session_limit` (detail `limit <n> client connections`, `limit <n> client associations`, either with `from one address`, or `the Agent's <n> descriptors for gateway clients are in use`). An open TCP connection gets no idle timeout, and each direction's end is passed on separately (half-close); once one side has ended its direction, the other ends after `idle_timeout_secs` without data, so a client that goes quiet after the engine closed does not keep its place. Client connections use TCP keepalive (after 60 s idle, every 15 s, 4 probes). A UDP association ends 5 s after it opened, whatever its client sends, until the client shows that it receives what the engine answers: the engine answers a valid QUIC Initial before any authentication (sing-box 1.14.4 does, tested), and anyone can make one, from an address that need not hear the answer (spoofed). A client shows it by addressing the connection ID the engine's first QUIC answer chose, as every QUIC packet after the first does; for Hysteria2 with obfuscation, whose QUIC headers cannot be read, by any datagram after an answer (an answer at all takes the obfuscation password). The obfuscation password is in every client's share link, so anyone who holds one can make an association from a spoofed address last as long as it keeps sending; the per-source and per-gateway bounds still hold it. Once shown, an association expires after `idle_timeout_secs` with no datagram either way, but never sooner than 31 s, so the engine's 30 s QUIC idle timeout (Hysteria2 and TUIC defaults in sing-box 1.14.4) ends quiet connections first. Sending a datagram back to a client waits for room on the public socket only as long as the association lasts: ending it never waits on a full socket. The public listener binds every address the gateway names; a gateway's `[::]` also takes IPv4 clients, as the engine did (a forwarding rule's own `[::]` stays IPv6 only). Gateways have one port each; port hopping is not offered.
- UDP datagrams cross the public listener in batches: those one client sent back to back that the kernel received together (UDP GRO) are judged together and passed on in one send that the kernel splits again (UDP GSO), each datagram keeping its own boundary; the engine's answers go back the same way. The extra hop costs CPU and latency rather than rate. Measured independently over loopback on one 8-core machine (release build, sing-box 1.14.4, client, engine and Agent on the same machine, medians of 33 alternating runs against 0.150.0, where the engine listens publicly): transfer rates were at least those of 0.150.0 (Hysteria2 upload 1.00 and download 1.14 times, Trojan upload 1.09 and download 1.08 times). The Agent's CPU per transfer rose from 0.73 to 1.81 s for Hysteria2, mostly kernel time (0.61 to 1.52 s: copying each datagram in and out and passing it over loopback once more), and from 0.81 to 1.04 s for Trojan. A 64-byte round trip took 225 to 314 µs at the median for Trojan (about 1.40 times; about 1.28 times at the 99th percentile), and about 1.04 times (median) and 1.07 times (99th percentile) as long for Hysteria2. With fewer cores shared by the engine, the client and the Agent, the extra CPU can cost Hysteria2 some rate.
- The Agent learns each inbound's loopback port from the pinned engine's own log (`inbound/<type>[in-<rule id>]: tcp|udp server started at <address>`), per engine start. Only a start that named a loopback port of the right transport for every gateway counts: until then, or when its log cannot be read, the start is not ready and no client is passed on. A configuration whose engine is not ready within 10 seconds is not applied and the previous generation is restored. When the engine restarts on new ports, client connections and associations made to the previous start end; clients reconnect to the new one.
- Reality's camouflage fallback, including for unauthenticated clients the public listener let in, traverses the bridge: it is metered, and the server's outbound rule set and the rule's destination lists apply to the camouflage destination (a refusal is a block record on the rule).
- In the connections view, gateway sessions are the bridge's sessions, with a loopback source. They cannot be ended from the panel: ending one would end only that proxied connection, not the client's outer TLS/QUIC connection, and the client could open another. Whether a client was refused is told by the public listener's block records.
- Native connection/session limits apply at the private bridge, including the Reality camouflage dialer. They do not bound all unauthenticated protocol handshakes from allowed sources. Host-level resource caps and ingress protections remain necessary for deployment capacity planning.
- The optional engine receives `GOMEMLIMIT=96MiB` and `GOMAXPROCS=1`. The Go memory value is a GC target, not a hard memory limit. Include the child process in an agent service cgroup when measuring or enforcing memory budgets. QUIC stream concurrency is bounded to the lesser of the rule connection limit and 128 per QUIC connection.
- QUIC servers and sing-box client exports start with a 1,200-byte packet payload, so initial packets fit a 1,280-byte path MTU. Path MTU discovery remains enabled. Other clients control their own initial packet size; do not assume every client's defaults work on constrained tunnel paths.
- Configuration and TLS material are checked before the active process is replaced. A private candidate generation has new bridge credentials. Startup or durable-save failure restores the previous engine generation. Applying a gateway generation briefly restarts the shared engine and interrupts its existing protocol connections; this is not a zero-downtime reload.
- While the Agent starts a process (the engine, at a gateway generation or after a crash; `ip` and WireGuard commands), the new process holds a copy of the Agent's sockets until it runs its program, for microseconds to a few milliseconds. A listener the Agent closes in that window stays open until then: a client that connects to it completes the TCP handshake and is then reset without a byte served, a datagram sent to it is dropped, and binding the same address again in that window fails with `EADDRINUSE`. An apply closes a listener and binds an overlapping one at once only when it moves a listener on the same port (`0.0.0.0` to an address of its own or back, a gateway between `0.0.0.0` and `[::]`) or rolls such a move back; it starts no process in between, and its own process starts return only once the program runs. If a process another task starts (an engine crash restart, an `ip` or WireGuard command) falls in between, that apply fails and the running revision stays: reopened, or reported closed until the next apply, which the next synchronization retries.
- Unexpected engine exits restart with bounded exponential delay. Shutdown stops the owned child. Linux also sets a parent-death signal. Temporary configuration directories use mode 0700 and files use 0600. Crash leftovers can contain secrets and should be handled as private node state.

Turning an enabled rule into a gateway whose public address is the address the rule listens on now, or a gateway back into an ordinary rule on its public address, requires disabling the rule, publishing that and waiting until the server applies it. The controller refuses such a publication with 409 `rule <name> listens on <address>: disable it, publish that and wait until the server applies it before turning it into a protocol gateway there or back`, judged against the configuration published before and every one the server may still run: those from the one it last reported applying on, or every one it was given after its Agent restarts and until it reports again, and while the server awaits a replacement Agent (a server whose Agent never connected runs none). Only rules a publication turns on, or moves to another listener or kind, are looked up in those; a rule it leaves listening as before is not, since an Agent running one of them would refuse the configuration published before as well. So while an Agent stays down after a restart, other publications go through, but a rule that once listened on that address as the other kind cannot be turned there, or turned on again there, until it reports, even when it is already of the kind it has now and was only disabled; the 409 text then still asks to disable it, and waiting for the Agent to report is what ends it. A new rule can. A server whose credential was revoked before any Agent connected is counted as one whose Agent did: a rule turned there is looked up in every configuration it was given. An Agent that still runs the rule enabled refuses the configuration and keeps the running one.

Changing inbound MPTCP is unsupported on gateway bridges. Native outbound MPTCP remains available when the destination supports it. The UI also preserves health-check settings on ordinary MPTCP relay rules; gateway rules have dynamic destinations and no fixed-target health probe.

## Acceptance scope

`tests/managed_gateways.rs` includes default validation/export checks and explicit engine-dependent tests:

```sh
RELAY_TEST_PROTOCOL_ENGINE=/absolute/path/to/sing-box \
RELAY_TEST_MIHOMO=/absolute/path/to/mihomo \
cargo test --locked --test managed_gateways -- --include-ignored --test-threads=1
```

The pinned acceptance clients are sing-box 1.14.4 and mihomo 1.19.33. `gateway_clients_are_judged_by_their_own_address_before_the_engine` and `reality_fallback_is_metered_on_the_bridge_and_held_to_the_outbound_set` check the public listener against the real engine (no Reality handshake or QUIC version negotiation for refused sources, IPv4-mapped and IPv6 clients, rule-set edits without an engine restart, a restart on new ports); `tuic_anytls_trojan_and_vmess_refuse_before_their_handshake` checks the other four protocols the same way (a refused source receives no byte of a TLS handshake or a QUIC answer, and is recorded); `quic_clients_are_not_the_rules_udp_sessions` checks that three Hysteria2 clients connect at once with `udp_max_sessions` 1; `quic_initials_hold_a_place_only_once_their_sender_shows_it_hears_the_engine` checks that the engine answers QUIC Initials made by the test, that senders that do not use the answer give their places back after a few seconds however often they send again, and that a sender that addresses the engine's connection ID keeps its place. Tests with a stand-in engine (no sing-box needed, run by default) check port discovery and its rollback (including a port named after the start line; in a process of its own, see below), IPv4-mapped and IPv6 clients of a `[::]` listener, half-close and the idle limit after it, the per-gateway, per-source and descriptor bounds (the last in a process of its own with a lowered limit), which clients show they hear the engine (by connection ID, by any later datagram when obfuscated, not by sending again) and expiry before and after, NAT rebinding, two datagrams of a new association arriving together, datagrams sent together (UDP GSO) arriving one by one in both directions on a `[::]` listener, or refused together and each recorded, keepalive on client connections, half-close from either side, a descriptor limit lowered while running, moving a gateway between `0.0.0.0` and `[::]` while hundreds of associations hold the old listener and handing its port to a forwarding rule, IPv4 listeners back after a move to `[::]` whose engine fails to start or whose configuration cannot be saved, a forwarding rule's failed move to `[::]` leaving its IPv4 listener and sessions as they were, turning an active rule into a gateway, and back, only once disabled, and a busy association yielding its thread to the rest of the Agent, so on a one-thread runtime the client's datagrams still reach the engine while the engine floods it with replies (this catches a regression reliably only on an idle machine with several cores; with 4 cores or fewer, or under load, it is a weak guard). The controller's refusal of that publication is in `tests/firewall.rs`. Unit tests in `src/engine/gateway_front.rs` check that datagrams sent together go out one by one where the kernel cannot split them, and that packet information cut short drops one datagram without an error or an ended association. The check that a failed start leaves the public port refusing connections, and the checks that close listeners and bind their ports again (a failed start reopening the wildcard it replaced, moves between `0.0.0.0` and `[::]` and their rollback, a rule turning into a gateway and back), run in processes of their own: a test that starts a process forks, and until the fork runs its program it holds a copy of every socket of the test process, so a listener another test just closed could take a connection, or keep its port from being bound again, for that while (see the process-start window above).

To compare transfer rate and CPU with and without the public listener, run the measurement once on this version and once on 0.150.0 with the same function copied into its `tests/managed_gateways.rs` (it uses only helpers both have):

```sh
RELAY_TEST_PROTOCOL_ENGINE=/absolute/path/to/sing-box RELAY_TEST_BULK_MIB=256 \
cargo test --locked --release --test managed_gateways hysteria2_bulk_transfer_rate_and_cpu -- --ignored --nocapture
```

It prints upload and download MiB/s over loopback and the CPU seconds of the Agent (the test process), the engine and the client. Fixtures exercise TCP for all six protocols, UDP for the five enabled for UDP, Reality/Vision, wrong credentials, a wrong Reality key, source/destination/private-address denial, zero quota, expiry, aggregate rate limits, exact payload accounting for certificate-mode protocols, metered Reality camouflage, private bridge authentication, child crash/restart, occupied-public-port rollback and missing-certificate preflight. Plain TLS fallback probes verify that zero quota and a denied camouflage destination cannot bypass the bridge. The mihomo TLS fixtures use an explicit leaf-certificate SHA-256 pin without disabling verification. A fixture-only DIRECT echo probe waits for mihomo forwarding readiness; the protocol transfers themselves are not retried.

These checks do not establish every GUI client's compatibility, WAN capacity, denial-of-service resistance or long-duration reliability. Version-specific execution results and outstanding deployment gates belong in the verification package.
