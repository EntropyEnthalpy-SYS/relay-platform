# 限速：上下行合计、分别限制上传 / 下载与突发

Relay 的限速有三个层级：**规则**、**服务器（节点）**和**用户跨节点总限速**。每个层级都可以设置上下行合计限速（原有的 `rate_bytes_per_sec`，行为不变），也可以只限上传、只限下载，或任意组合；设置了的各项限速同时生效。规则和服务器的每项限速还可以带**突发**（英文界面 Burst）：在一段时间内高于限速运行，用完突发额度后回到限速。它对应 Zero Forwarder 文档中的“分别设置上传 / 下载限速”和“动态限速”。

用户跨节点总限速不支持突发。

## 方向

- **上传**：本跳的客户端发往目标的字节；**下载**：目标返回客户端的字节。UDP 相同：客户端发出的数据报是上传，目标的回复是下载。
- 方向按**每一跳自己的客户端**计算。多跳路径上，下一跳的客户端是上一台服务器，所以用户发出的数据在每一跳都是上传。
- 代理服务（Shadowsocks、SOCKS5、HTTP CONNECT、HTTP/2 CONNECT、受管协议网关）中，客户端发往其请求目的地的是上传；反向隧道的公网端中，用户发往内网目标的是上传。
- 计量、额度、共享预算和流量账本不变：仍按上下行分别计数、合计扣量，限速只决定发送的快慢。

## 层级与字段

| 层级 | 合计（原有） | 新增 | 界面 |
| --- | --- | --- | --- |
| 规则 | `Rule.rate_bytes_per_sec` | `Rule.rate_limits` | 规则编辑器（合并配额之后），bytes/s |
| 服务器 | 节点配置 `rate_bytes_per_sec` | 节点配置 `rate_limits` | 转发规则 → 按服务器 → 节点总限速，Mbit/s |
| 用户总限速 | 元数据 `user_rate:<用户>` | `user_rate_upload:<用户>`、`user_rate_download:<用户>` | 用户与权限 → 总限速，Mbit/s |

`rate_limits` 的形状（规则和服务器相同，各字段未设置时省略，空对象等同于没有）：

```json
{
  "upload_bytes_per_sec": 2500000,
  "download_bytes_per_sec": 6250000,
  "burst": {"bytes_per_sec": 25000000, "secs": 60},
  "upload_burst": {"bytes_per_sec": 5000000, "secs": 300},
  "download_burst": {"bytes_per_sec": 12500000, "secs": 300}
}
```

- `burst` 附在合计限速 `rate_bytes_per_sec` 上，`upload_burst` / `download_burst` 附在对应方向的限速上。
- 校验（400）：每项速率 1..=10^12 bytes/s；突发必须有对应的限速；突发速率 B 必须大于该限速 S 且不超过 10^12；突发时长 W 为 1..=86400 秒。用户总限速每个方向为 1024..=2^40 bytes/s，与合计相同。
- 规则限速由该规则的全部会话共享；服务器限速由这台服务器的全部规则共享；用户总限速由该用户在全部服务器上的规则共享，控制器把它拆成各服务器的份额（见下文）。
- 一次发送依次等待：规则的合计限速和本方向限速、用户在本服务器的合计份额和本方向份额、服务器的合计限速和本方向限速。取最严的一项。公平排队（先在用户之间轮转，再在同一用户的连接之间轮转；小的读写不排在大传输之后）对每一项限速都适用。

## 突发模型

一项带突发的限速有持续速率 S、突发速率 B（B > S）和突发时长 W 秒：

- 突发额度的容量为 (B − S) × W 字节，**开始时是满的**。
- 额度未用完时，流量最快可以达到 B；高于 S 发送时按 (速率 − S) 消耗额度，低于 S 发送时按 (S − 速率) 恢复额度，最多恢复到容量。
- 额度用完后，限速为 S。

例：突发 100 Mbit/s、持续 30 Mbit/s、突发时长 5 分钟。额度为 (100 − 30) Mbit/s × 300 秒 = 21,000 Mbit（2,625 MB）。满额时以 100 Mbit/s 运行 5 分钟，之后为 30 Mbit/s；链路低于 30 Mbit/s 运行时额度逐渐恢复，从空闲开始约 11.7 分钟（700 秒，加下文的 1 秒）后恢复满额。

实现（`crates/relay-platform/src/engine/rate.rs`）：

- 每项限速用两个令牌桶。**持续桶**以 S 补充，最多存 1 秒的 S（至少 64 KiB，即一次完整读取，与以前的限速桶相同）加上额度容量；**峰值桶**只在有突发时存在，以 B 补充，最多存 1 秒的 B。一次发送要两个桶都够才放行。持续桶中超过 1 秒 S 的部分就是突发额度：以速率 r 发送时持续桶每秒净变化 S − r，正好是上面的消耗 / 恢复规则；峰值桶把速率限制在 B。
- 因此从空桶恢复时先补满那 1 秒的 S，再恢复额度；上例中完全恢复需要 701 秒。
- 没有突发的限速与以前完全相同：一个桶，容量 1 秒的 S（至少 64 KiB）。
- 修改限速时保留桶中的令牌，按新的大小截断；给原来没有突发的限速加上突发时，额度从满开始；Agent 重启后所有额度从满开始。
- 计算全部以传入的时间为参数，单元测试用合成时钟逐步验证消耗、恢复和封顶（`engine::rate::tests`）。

额度状态：支持新限速的 Agent 在统计中回报 `stats.rate_limits.bursts`，每项带突发的限速一条 `{rule_id, direction, credit_bytes, capacity_bytes}`（服务器自身的限速 `rule_id` 省略）。面板在规则列表的“配额 / 限速”列和“按服务器”中节点总限速标记旁显示“突发额度 N%”，低于 100% 表示额度正在使用或尚未恢复。

## 用户总限速的分方向份额

合计、上传、下载三项总限速各由一个独立的分配器拆成各服务器的份额，规则与原有合计份额相同：按各服务器的实测用量动态分配，忙的服务器多分；一台服务器的份额只会增长到其他服务器未持有的部分，所以在所有服务器同步过之后，同一方向生效中的份额之和不超过该方向的总限速；服务器与控制器失联 15 秒后退回平均份额。`GET /users/{id}/rate` 返回 `nodes`（合计）、`upload_nodes`、`download_nodes` 三组份额。

Agent 在同步中按方向回报计数：`UserRateReport.upload` / `download`（`{bytes, waited_ms, enforced_bytes_per_sec}`）。份额 `UserShare` 在只有合计时与以前的格式完全相同；有上传 / 下载份额时增加 `upload` / `download`（`{rate_bytes_per_sec, fallback_bytes_per_sec}`），只有分方向限速的用户省略合计字段。

## 兼容性与旧 Agent

- 原有字段和行为不变：只设 `rate_bytes_per_sec` 的配置、备份、API 调用与以前完全相同；新字段未设置时不出现在任何配置、份额和统计中。旧记录、旧备份读取时新字段为空。
- Agent 的 `Rule`、节点配置和份额拒绝未知字段，所以早于本版本的 Agent 会拒绝带新字段的配置。控制器与反向隧道相同地按能力下发：
  - 控制器在同步响应中带 `rate_limits: true`（旧 Agent 忽略同步响应中的未知字段）；新 Agent 看到后在统计中回报 `rate_limits`（可以是空对象）。
  - 控制器第一次收到时写入元数据 `rate_limit_node:<节点 id>`，此后这台服务器视为支持；删除服务器时一并删除。`GET /nodes` 的 `rate_limit_support` 显示该状态。
- 没有该记录的服务器：
  - 发布任何带 `rate_limits` 的规则或节点配置返回 **409**，原因为 `the agent on server <名称> is too old for separate upload/download or burst speed limits; upgrade it first`，从未连接过面板的服务器为 `server <名称> has not connected to the panel yet; separate upload/download or burst speed limits need its agent to report in first`。检查在所有发布路径的同一处进行：单节点发布、批量预览和发布、回滚、模板、共同规则、链路、反向隧道和跨面板共享。
  - 给用户设置上传或下载总限速时，承载该用户启用规则的服务器中只要有一台不支持，返回 409（同上原因）。用户已有上传或下载总限速时，在不支持的服务器上发布该用户的启用规则也返回 409：`user <用户名> has separate upload/download speed limits: <原因>`。这样限速不会在某台服务器上被静默丢弃。
  - 合计份额照常下发；上传 / 下载份额只发给支持的服务器。
- 面板把这些 409 原因翻译为界面语言显示，节点总限速对话框在服务器尚未回报支持时提示先升级 Agent。
- 已回报支持的 Agent 如果被降级到旧版本，控制器仍会下发新字段，旧 Agent 拒绝该配置并回报应用错误；请升级 Agent 或删除新限速。

## 各功能中的限速

| 功能 | 处理 |
| --- | --- |
| 规则编辑器 | “限速方式”选择上下行合计 / 分别限制上传和下载 / 合计并分别限制；可选突发（每项一组突发速率和突发时长）。单位 bytes/s |
| 节点总限速 | 同上，单位 Mbit/s；`PUT /nodes/{id}/config` 省略 `rate_limits` 保留，`null` 取消 |
| 用户总限速 | 限速方式同上，无突发；分方向显示各服务器份额 |
| 共同规则、模板 | 规则副本携带 `rate_limits`，漂移检查包含它 |
| 链路 | 生成的各跳不带限速（与合计限速相同），之后可在规则编辑器中修改各跳 |
| 反向隧道 | 公网端规则的 `rate_limits` 可以在“访问与限速”中修改，与 `rate_bytes_per_sec` 相同 |
| 跨面板共享 | 共享可设 `upload_bytes_per_sec` / `download_bytes_per_sec`，与 `rate_bytes_per_sec` 相同：作用于共享的每条规则，也作为共享账户在这些规则上的总限速。共享所在服务器不支持时 409；接收方面板发布时修改共享规则的限速返回 400 |
| 诊断导出 | `rate_limits` 不含秘密，原样导出 |

- 集成测试 `tests/rate_limits.rs`：真实 Agent 经 API 验证规则和服务器的单方向限速及规则突发，用户上传 / 下载总限速在两台服务器之间的份额，UDP 方向，旧 Agent 的 409，以及不含新字段的记录和配置读写不变。
