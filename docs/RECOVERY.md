# 控制器恢复日志与操作步骤（0.4.0 起）

此版本可用旧控制器数据库备份，加上完整的后续恢复日志，重建已经提交的节点身份、用户权限、会话、配置、计量、预留和审计记录。它不恢复两端都丢失的节点用量，也不替代密钥迁机或异地备份系统。0.13.0 的节点执行租约随日志保存策略和运行身份，控制器重启按完整 TTL 保守等待接替，见 [NODE_LEASES.md](NODE_LEASES.md)。

0.18.0 的[签名部署工具](LINUX_DEPLOYMENT.md)将程序代次与运行状态分开。程序 `rollback` 只切换可兼容的二进制/配置，不复制旧数据库，也不回退 `recovery.log`。部署工具的 `recover` 恢复安装或卸载意图；本页的 `relay restore` 重建控制器状态，两者处理不同的持久记录。

## 需要保存的文件

- 用 `relay backup` 生成、且生成于恢复日志启用之后的控制器数据库备份。
- 同一控制器的完整 `recovery.log`，从文件头到最新已提交记录。
- 该日志相邻的 `recovery.log.head.json`，它声明最新事务序号、提交字节数、数据库结构校验值和日志链校验值。
- Agent 私有状态库、证书、CA、私钥另行保护；控制器备份不包含这些节点文件。

`relay server` 默认把日志写到 `STATE/recovery.log`。可用 `--recovery-log /private-volume/controller-recovery.log` 指定另一个已存在的目录，相应进度清单会命名为 `controller-recovery.log.head.json`。目录不能由组或其他用户写入，日志和清单要求私有权限 0600。日志持有独占文件锁，恢复命令不能同时读取仍在运行的日志写入器。

默认数据库和日志位于同一状态目录；该默认布局不能抵御整块磁盘丢失。此版本没有异地复制、自动归档、压缩或日志轮换，心跳写入也会累积日志。应监控文件增长；不能删除旧记录或自行截断日志。复制一份旧日志和旧清单不会使它们自动变成最新记录。

## 创建与恢复

启动新控制器或升级当前正常运行的 v1/v2/v3 状态库后，先生成新的恢复基线：

```sh
relay server --state ./state/controller --listen 127.0.0.1:8080
relay backup --database ./state/controller/controller.sqlite --output ./backups/controller.sqlite
```

第二条命令可以在另一个终端、控制器运行期间执行；备份由 SQLite 一致性备份接口生成，不覆盖现有文件。后续操作写入原控制器日志。

恢复时：

1. 停止原控制器及其他同身份副本。文件锁只保护本机同一路径，不能阻止另一台机器上的副本。
2. 保管原备份、完整最新日志及其清单；在静止状态复制日志和清单，避免混用不同时间的文件。
3. 选择一个尚不存在的输出目录。父目录应已经存在。
4. 执行恢复并检查退出码和 JSON 报告：

```sh
relay restore --backup ./backups/controller.sqlite \
  --recovery-log ./state/controller/recovery.log \
  --output ./state/restored-controller
```

5. 使用恢复出的新状态目录启动控制器，再验收节点心跳、实际转发和计量：

```sh
relay server --state ./state/restored-controller --listen 127.0.0.1:8080
```

恢复结果包含 `controller.sqlite`、`recovery.log` 和 `recovery.log.head.json`。原输入不会被修改。管理员密码和会话以数据库状态为准，恢复不会重新创建初始密码文件；原密码必须另行掌握。不要同时重启旧控制器与新实例。

报告中的 `backup_sequence` 是备份检查点，`restored_sequence` 是最新完整提交，`replayed_transactions` 是重放数量。`budget_allocation_paused` 反映恢复后的真实状态：源控制器未隔离时，完整重放后可以继续分配；源控制器原本隔离时仍保持隔离。`ignored_uncommitted_tail:true` 表示日志末尾存在未完成提交，其内容没有被当作已确认事务重放。

## 写入和拒绝条件

每个非空控制器数据事务依次执行：

1. 收集 SQLite Session changeset，追加准备记录并同步日志。
2. 在同一 SQLite 事务写入恢复检查点，提交数据库。
3. 追加日志提交记录并同步，原子替换进度清单并同步所在目录。
4. 返回写入成功。

0.5.0 的节点同步可以在同一事务合并至多 16 项请求，每项请求在独立保存点内验证和执行。输入错误回滚该项，其他有效请求可一起提交；任何存储或最终日志确认错误均不会返回部分成功。一条日志记录可包含多个节点的变更，事务序号不是同步请求数。日志格式、数据库版本和上面四个持久化步骤不变。

准备记录之后崩溃但数据库尚未提交时，正常重启丢弃未提交尾部。数据库已经提交、日志提交记录或进度清单尚未完成时，正常重启用实时数据库的检查点确认并完成提交。旧备份不能用于猜测这个未完成边界；恢复命令只接受进度清单与日志完整提交一致的历史。

日志写入或清单更新失败后，进程拒绝后续写入，`/healthz` 返回 503。应先修复存储问题，再使用原数据库和原日志重启以协调状态。已启用日志的数据库不能不带日志继续写入，也不能把一份较旧数据库直接接到较新的日志上运行。

以下情况会拒绝恢复，且不会留下半成品输出：日志缺失、缺少最新清单、校验不一致、提交记录被截断、日志属于另一控制器、备份检查点不在日志中、数据库结构不匹配、重放冲突、外键或完整性检查失败。已有输出目录保持原样。发生错误时保留原始文件，不要手动改恢复检查点或额度隔离标记。

## 明确边界

- 目前只支持 schema v4 的控制器日志和备份。升级前的旧备份缺少连续恢复证据；应升级当前正常状态后生成新基线。将来数据库结构升级也需要明确的日志迁移方案，不能直接混用。
- SHA-256 链用于检测内容损坏、缺段和与清单不一致；不是签名，也不能证明同时回退的日志与清单足够新。必须可靠保留最新一对文件。
- 重放采用冲突即失败，不能把手动修改后的数据库当作原备份强行覆盖恢复。
- 正常恢复可以重放已保存的用户会话、撤销和节点身份；严格节点的单控制器执行租约随之恢复，不能推定为多控制器共识。0.16.0 已接入[凭据轮换任务、退役标记和回执恢复](NODE_CREDENTIALS.md)，0.17.0 增加[撤销、替换令牌和旧配额周期保护的恢复](NODE_IDENTITY.md)。
- 0.14.0 的 Agent 可在原状态完整、所有权连续时在线验证和补报，再延续原预算运行；控制器必须保留完整历史且未隔离。受管备份移除续接资格，未知消费仍保守占额。控制器日志不能推断丢失节点磁盘上的最终消费量，不能自动退款，见 [BUDGET_RECOVERY.md](BUDGET_RECOVERY.md)。
- 本地测试覆盖四个持久化边界的子进程突然退出、清单写入失败、损坏/截断/外来日志，以及旧备份恢复后的真实 TCP 续传。没有执行实机断电、异地存储损坏或整盘丢失演练。

可重跑的 Release CLI 演练：

```sh
python3 scripts/check_recovery.py --output artifacts/recovery-smoke.json
```

它创建临时控制器和 Agent，在节点建立之前生成备份，之后停止控制器并恢复；同一 TCP 连接继续收发并领取新额度，最后核对节点、控制器和额度三份账。所有子进程都会清理，不安装服务。

## 0.15.0 节点资料恢复

节点名称与 profile 的修改、修订和审计在同一事务进入现有日志。完整重放保留类型、分组、标签、备注、精确成本以及 enabled/expires_at_ms。独立 Release 演练从资料修改前的备份重放，逐字段比对最终资料，同时核对真实暂停、断联到期和延长后的业务账本。它不恢复较旧日志所遗漏的资料，也不证明错误系统时钟下的日历到期正确。

## 0.16.0 节点凭据恢复

轮换任务、当前凭据哈希、退役哈希标记和完成回执进入控制器事务日志。使用轮换前的旧备份加完整日志恢复后，所有已退役凭据继续被拒绝。Agent 在私有状态库保留未确认候选，提交前后突然退出都可以使用同一候选继续；没有本地候选时，旧凭据和原注册令牌不能恢复已经轮换的身份。新 Agent 必须先确认租约和账本规则再运行，轮换不放宽原有预算恢复条件。详情见 [NODE_CREDENTIALS.md](NODE_CREDENTIALS.md)。

## 0.17.0 撤销与替换恢复

撤销回执、当前身份阶段、注册令牌有效期、退役长期凭据/注册令牌标记、操作摘要和历史规则周期保护随日志恢复。旧操作精确重放返回当前状态，不再次撤销后来注册的身份，也不恢复旧令牌或延长到期时间。新注册实例使用全新私有状态；旧状态的未知消费和预算预留继续保留，不能因换身份而退款。冷启动仍保留完整租约 TTL 等待。独立 CLI 同时校验已知账本与实际未上报消费，详情见 [NODE_IDENTITY.md](NODE_IDENTITY.md) 和 replacement-smoke.json。
