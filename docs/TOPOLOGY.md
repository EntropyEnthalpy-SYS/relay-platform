# 声明式多跳与多节点配置发布

0.9.0 使用节点规则作为拓扑的唯一配置来源。目标可引用另一个节点的规则，该规则再指向后续节点或最终服务；一条规则的多个目标始终是并列候选，不是顺序中转。多入口可以汇入同一下游，已有三种分配策略和权重继续生效。

## 节点端点和边

下游规则用 `advertise` 声明前一节点可以连接的地址，例如：

```json
{
  "id": "middle-rule",
  "listen": "0.0.0.0:19002",
  "advertise": "middle.example.com:19002"
}
```

以上为规则字段片段，其他必需字段仍须提供。监听可以是通配地址，但 `advertise` 必须是具体 IP 或 DNS 名称加端口。它不会创建 DNS 记录、NAT 映射或防火墙规则；实际可达性需要另外探测。允许 NAT 场景的对外端口与本机监听端口不同。

上游目标同时保留实际拨号地址和明确引用：

```json
{
  "address": "middle.example.com:19002",
  "weight": 1,
  "via": {"node_id": "已注册的节点ID", "rule_id": "middle-rule"}
}
```

目标地址必须与被引用规则的 `advertise` 相同。比较时规范化 IP 表示、DNS 大小写与末尾点，以及端口数值；不会在控制器发起 DNS 解析。IPv4 映射 IPv6 使用既有规范化规则。单租户内相同地址、端口范围和传输协议不能声明两次；TCP 和 UDP 的不同端点分别检查。

跨节点引用必须满足：

- 节点与规则都存在，且规则属于被引用节点；上下游在同一租户。系统管理员也不能绕过跨租户共享授权，后续资源共享模块另行实现。
- 被启用的上游不能指向已停用的下游。停用下游时，应在同一批次停用全部受影响的上游。
- 下游接收上游使用的全部传输协议；偏移端口映射要求下游端口段足够长，声明端口段不能溢出。
- TLS 开关一致；要求客户端证书时，上游必须配置客户端证书编号。不同节点上的 CA、证书和私钥是否真正匹配，仍由节点握手验证。
- WS 路径、Host、Origin 与下游接收策略匹配；PROXY 的版本、位置相容。真实代理来源 CIDR、路由、防火墙及证书内容不能仅靠声明证明。
- 所有声明边组成有向无环图，包括停用规则的边。单节点编辑、批量编辑和历史回滚都执行同一检查。已知 `advertise` 地址不能通过去掉 `via` 变成普通目标来绕过检查。

控制器只保证**声明的引用和地址图**。没有枚举 DNS 别名、NAT 回流、第三方代理或所有物理网络路径；不同声明地址实际映射到同一端口等情况仍需网络规划和实机验收。Agent 既有本机静态/动态环路检查继续生效。

## 预览与事务发布

`GET /api/v1/topology` 返回当前可见节点、期望配置、声明边、根规则及逐节点应用状态。只读用户可以查看本租户；不能预览写操作或发布。

`POST /api/v1/configurations/preview` 与 `POST /api/v1/configurations/publish` 接受相同请求：

```json
{
  "updates": [
    {"node_id": "入口节点ID", "expected_revision": 3, "rules": []},
    {"node_id": "中转节点ID", "expected_revision": 5, "rules": []}
  ]
}
```

示例的空数组意味着删除该节点所有规则，并非“保持不变”。实际发布须保留每个节点已有的无关规则。一批 1..64 个不同节点；HTTP 请求上限仍为 2 MiB。每项携带该节点当前修订，任何一项过期则整批返回 409；修订不能超出既有整数范围。

预览不改数据库、修订、规则绑定或审计，返回规范化后的候选配置和 `changes`。每项差异包含新增/修改/删除规则 ID，以及 `rule_changes` 中精确的 `before`/`after` 规则；控制器自动绑定的层级额度也在预览里可见。

发布重新校验权限、修订、所有者、预算、监听、引用、协议和环路。各节点期望修订、配置历史、规则/周期绑定及审计在**一份 SQLite 事务和一份恢复日志事务**中提交。任一数据库写入失败则整批回滚；日志未确认时不返回成功。已有单节点 PUT 与历史回滚也走这一实现。

这只是控制器期望配置的事务原子性。各 Agent 独立轮询、准备监听和应用；不能把批次提交成功解释为全部节点同时上线。端口占用或材料错误时，该节点保留旧配置并通过 `apply_error` 回报，其他节点可能已应用。页面逐项展示实际/期望修订、错误和活跃会话；没有自动灰度、跨机器原子切换或业务健康保证。

## 改向前的停止确认

节点已经发布过的拓扑规则，不能在启用状态直接改监听、可达地址、下一跳、DNS/出口绑定或传输组合，也不能直接删除。执行顺序为：

1. 保留路由结构，在同一批次停用关联链路。
2. 等相关节点确认该期望修订、没有应用错误，并回报 `active_tcp=0`、`active_udp=0`。
3. 预览并发布改向后的配置，或删除/重新启用规则。

确认范围目前是整个涉及节点的活跃会话（0.10.0 同时要求活跃探测数为零），因此无关规则仍有会话时也会保守等待；后续需要细化到规则级确认。未注册节点没有受管运行身份，可在注册前编辑。节点首次配置未确认、离线而仍有旧状态或报告非零会话时不会跳过屏障。

换一个规则 ID 复用仍在停止中的监听地址/端口，也需要上述确认，不能用“删除旧规则、创建新规则”绕过。节点本地拓扑路由变化会取消相关旧运行代次；正常的权重、均衡调整仍可按已有转发约定处理。停止屏障与执行租约分别验证。0.13.0 严格节点通过运行凭证约束同一身份的协作式 Agent，新持有者必须重新报告配置与状态；离线节点仍不提供复制身份互斥，见 [NODE_LEASES.md](NODE_LEASES.md)。

## 计量与界面

每跳使用已有独立规则账本。同一段应用数据经过三跳，每条规则都记录接纳量；若三个规则属于同一用户预算，该预算累计三跳用量。当前没有宣称“一条逻辑流只收费一次”，逻辑链路计费和共享资源计量仍需后续模型。

“多跳拓扑”页提供顺序链路向导、逐节点应用状态、关联组件启停和批量预览。向导支持原生 TCP/UDP、WS、双向证书 WSS；填写每跳监听、可达地址及必要证书服务名，节点证书须提前准备。普通规则编辑器可以选择下一跳规则和配置候选目标。成对调整传输参数时使用批量编辑，避免两端配置不一致。

关联组件启停会包含共享下游的其他入口，预览列出全部受影响节点和规则。高级批量编辑使用原始配置，仍执行同样的服务端权限和验证。页面当前通过源码与 JavaScript 语法检查，尚未通过浏览器视觉与点击验收。

## 升级、恢复与验证

数据库 schema v4、节点累计账本和恢复日志格式不变，新增字段直接进入既有配置历史。拓扑发布会作为完整单事务重放，不存在一半节点新、一半节点旧的恢复结果。先升级控制器和全部相关 Agent，再发布 `advertise` / `via`；0.8 严格解析器不接受这些字段，包含新字段的状态不应直接降级给旧控制器。

`scripts/check_topology.py` 使用实际 Release CLI 启动临时控制器和三个独立 Agent 进程，验证原生 TCP/UDP、WS 和双向证书 WSS 三种链路，并组合 PROXY v2。每组执行只读预览、整批发布、真实双向流量、停止确认、方向反转、逐跳账本核对和旧备份恢复；恢复后复核拓扑、账本和旧管理会话。

```sh
work/ws-interop/bin/python scripts/check_topology.py \
  --binary target/release/relay --output artifacts/topology-smoke.json
```

测试环境使用 `scripts/requirements-interop.txt` 中的隔离依赖和临时证书工具，具体结果见 [VALIDATION.md](VALIDATION.md)。这些本机进程测试不代替真实 Linux 节点、广域网、故障选路、灰度切换或全部拓扑模块验收。

## 0.10.0：业务探测与停止屏障

`health_check` 可沿目标实际路径发送请求并检查回复；`via` 仅声明关系，仍不能替代真实回复。目标优先级、容量和 TCP/UDP 独立状态见 [HEALTH.md](HEALTH.md)。一次探测通过仅证明当次实际选中的下游路径，不能证明所有候选都健康。源节点诊断流量单列，下游受管规则正常计量。

停用配置会取消对应探测，改向或重新启用时控制器还会检查节点最后上报的 `active_probes == 0`。屏障仍基于受管实例最后确认的状态；仍不能替代物理拓扑发现或分布式原子切换；严格节点另外受 0.13.0 执行租约约束。
